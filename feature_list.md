### F-RECOVERY-UNBOUNDED — bound + parallelize partition recovery (3 bugs a fable subagent found)
- **Trigger** (2026-07-13, user pushed back on "150 GB → slow reopen" hand-waving: by design recovery should be bounded — replay from the SST max vp_head, read only SST index/bloom, fast commit_length — "否则就一定有BUG"; a fable subagent confirmed 3 real bugs). All three attack the same symptom: a PS that inherits partitions (full takeover after a sibling PS dies) reopens far too slowly and unbounded.
- **BUG 1 — F120-B WAL-gap force-rotate measured the wrong bytes.** The `MAX_WAL_GAP` (2 GiB) force-rotate compared `active.mem_bytes() + Σ imm.mem_bytes()` — the memtable FOOTPRINT. For a large-value (VP) workload the memtable holds only the ~24-byte ValuePointer while the 8 MB value sits in log_stream, so the gap NEVER approached 2 GiB → active never force-rotated → the un-flushed log_stream replay window grew **O(dataset)** (the real cause of unbounded recovery, not "150 GB is just big"). **Fix**: a new `Memtable.log_bytes: AtomicU64` tracks the ACTUAL log bytes appended (value included), fed from `finish_write_batch` (Σ `record_sizes`), the GC multi-frag rewrite (Σ appended), and recovery-replay (per-record V1 envelope + payload header + key + value); the F120-B check now reads `log_bytes()` not `mem_bytes()`.
- **BUG 2 — GC replay-floor pinned to the OLDEST live SST's vp_head (over-conservative → disk debt + recovery re-read).** `gc_replay_floor` = MIN stream-position over ALL live SSTs' vp_heads, which drags GC's punchable frontier (and, transitively, recovery's replay window) back to the oldest live SST — far behind the region actually needed. A fable subagent designed the **provably-loss-free** fix (Option C — NOT the naive "MIN→MAX in recover_partition", which is UNSAFE: it deletes the `chosen_pos==usize::MAX` no-replay rescue and reopens the post-merge q-key loss). Option C: **do NOT touch `recover_partition`**; raise ONLY the GC floor to the newest **DURABLY-ACKed flush checkpoint vp** (`PartitionData.durable_ckpt_vp`, set ONLY after `save_table_locs_raw` acks — never from in-memory `vp_*`/reader-MAX, which can run ahead of the durable checkpoint and punch a log region whose naming checkpoint never landed → silent loss). Every record strictly below a durable checkpoint vp is in that checkpoint's persisted SST set (or compaction-dead), so `[MIN-over-SST-vps, durable-vp)` is safe to reclaim. The recovery-read half self-resolves: once GC punches the covered prefix, those extents vanish from `log_extent_ids`, their SST vp_heads become unresolvable, recovery's Step-2 per-SST pass skips them, and `chosen_pos` naturally lands at the first surviving position — zero recovery-code change. Helper `gc_floor_raise_to_durable_ckpt` (max, ack-gated, no-op pre-first-flush / on unresolvable eid).
- **BUG 3 — `sync_regions_once` opened partitions SERIALLY (×N recovery).** Each `open_partition().await` returns only after the partition's own thread finishes `recover_partition` (log replay) + bind + register; awaiting them one-at-a-time made an N-partition takeover pay ~N× the single-partition recovery wallclock (×32 measured). Each recovery runs on its OWN OS thread/core and is latency-bound, so opening them **concurrently** (`buffer_unordered(OPEN_PARALLELISM=64)`) overlaps the waits. Gating (already-open / backoff / budget, with local budget reservation) applied UP FRONT to preserve the exact serial semantics; per-partition port-ord reservation + per-partition owner-lock keys already made concurrent opens race-free.
- **Acceptance**: PS unit tests green incl. new `background::gc_replay_floor_tests` durable-ckpt raise cases (advances floor + frees covered prefix; never lowers the MIN; no-op pre-first-flush/unresolvable) + `guard_punches_only_below_floor` still protects the vp extent; a takeover recovers in ~single-partition time, not ×N; no data loss across kill+restart. Reproduce-first system test `system_gc_floor_durable_ckpt.rs` (subagent-designed Scenarios 1-4, incl. the `set_flush_commit_pause`-armed durability race) is the recommended cross-host guard — DEFERRED (needs etcd + a new flush sync-point; local multi-tenant box blocks EN bring-up).
- **Status**: `passes: true` (2026-07-13; coco + BUG1 reproduce tests added 2026-07-14) — partition-server builds clean, **195 lib tests green** (+3 durable-ckpt floor-raise for BUG2, +2 new `bug1_wal_gap_tests` for BUG1 — the previously-UNCOVERED "real unboundedness": 2.4 GiB of VP writes → `mem_bytes` stays < gap (old signal never rotates) while `log_bytes` crosses `max_wal_gap()`), workspace builds (minus the pre-existing macFUSE `fuser` build.rs env failure, unrelated). **coco findbugs DONE 2026-07-14 (GPT-5.5, deep, HEAD~1..HEAD): NO P0/P1/P2 — BUG1/BUG2/BUG3 all pass correctness scrutiny.** BUG2 data-safety (the user's concern) confirmed: the ack-gated `durable_ckpt_vp` is set ONLY after `save_table_locs_raw().await?` (lib.rs — never from in-memory `vp_*` / compaction, the loss trap), the raise helper only ever `max`es the floor (never lowers, no-ops on 0/unresolvable), and the relocate-then-punch invariant it rides is system-tested (system_gc_multiversion_same_extent / system_vp_after_split_gc, both green here). One **P3 FIXED**: `MAX_WAL_GAP` was documented as "2 GiB" in the BUG1 comment / docs/ops.md / CLAUDE.md but the real shipped default is **1 GiB** (`max_wal_gap()`) — corrected in all three + the new test reads `max_wal_gap()` so it can't drift. BUG 1 + BUG 3 land the bounded + parallel recovery win; BUG 2 is the provably-safe GC-floor tightening (recovery replay path untouched by design). **Reproduce-first `system_gc_floor_durable_ckpt.rs` DONE + RED-GREEN VERIFIED (2026-07-14, heavy — `#[ignore]`, ~95 s):** it writes >1 GiB of 8 MiB VP values to roll a real log extent, force-GCs the FIRST extent E0 (which holds the oldest live SST's vp_head = the MIN floor, so it is punchable ONLY under the durable-ckpt raise), asserts E0 is RECLAIMED (proves the raise fired — baseline MIN protects it), then crashes + same-id-takeover restarts and asserts ZERO data loss (4 "cold" keys living in E0 are relocated-then-punched and recovered via replay + the 8 latest hot keys + a complete range scan). Genuine discriminator: with the raise NEUTERED (`gc_floor_raise_to_durable_ckpt` → `min_floor`) the run FAILS at the reclaim assertion ("E0 was NOT reclaimed … the raise did not fire"); with the fix it PASSES. Live cross-host takeover-timing (wallclock) verification still deferred to a cluster run.

### F-OVERVIEW-OPENTAIL — cluster overview must count open-tail bytes (0 B is wrong for compacted/log-heavy partitions)
- **Trigger** (2026-07-05, user hit it live: `autumn-op info` showed part 17 as `0 B  3 ext` while `info --part 17` reported 1.5 GB — "0B，应该是显示不对"): `compute_cluster_overview_resp` (manager) sums ONLY each extent's manager-authoritative `sealed_length`, and an OPEN extent's `sealed_length` is 0. A partition whose data lives entirely in open tails (major-compacted → fresh open row tail + a big open log tail; or any log-heavy partition) renders 0 B even though it holds GBs. The per-partition detail (`info --part`) probes the EN for open-tail live length, but the top-level overview deliberately does not (one-RPC / scalable). User decisions (via AskUserQuestion): size semantic = **total extent footprint** (Σ committed bytes across the 3 streams' extents, matches `info --part`), mechanism = **PS reports it** (no per-EN probe in the overview).
- **Scope**: (A) `PartitionLoad.open_tail_bytes: u64` (rpc, **WIRE v15** fp `4bbbbf8faeb05923`, MIN=MAX=15 same-commit) — PS-reported Σ committed length on the partition's log/row/meta OPEN tails. (B) PS: `PartitionMetrics.open_tail_bytes` + `open_tail_probe_inflight`; `background_maintenance_loop` runs a throttled (30 s) NON-BLOCKING probe — a detached task does `commit_length` on the 3 stream tails and stores the sum (kept at prior value on any error; a partial 3-tail sum would misreport). Detached because `commit_length` is up to 15 s worst-case (all-replica) and must never stall GC/compaction on the shared maintenance task. `report_load_loop` ships it. (C) manager `compute_cluster_overview_resp`: `live_size = Σ sealed_length + open_tail_of(pid)` (latest window bucket, 0 → sealed-sum-only fallback). Dashboard `/api/overview` inherits the fix (same builder). (D) manager/ps/rpc CLAUDE.md notes; docs/ops.md.
- **Acceptance**: `autumn-op info` part-with-only-open-tails shows a non-zero size matching `info --part <id>`; no per-EN probe in the overview path; wire tests green (v15 pinned); build + clippy clean (no new warnings).

### F-PS-SIZE-BYTES-DEAD — revive the dead `PartitionLoad.size_bytes` gauge (Prometheus + size-based policy)
- **Trigger** (2026-07-05, found while fixing F-OVERVIEW-OPENTAIL): `PartitionMetrics.size_bytes` (doc-commented "SST total + active.bytes + Σ imm.bytes, updated after each flush + rotate") has **NO writer anywhere** — it is a constant 0. Consequences: (1) the Prometheus `autumn_ps_partition_size_bytes` gauge always reads 0; (2) the manager's **size-based auto-split/merge policy** (`policy.rs` `split_size_hard` / `split_size_min` / `merge_size_low`) runs against a constant 0 → split-by-size can NEVER fire and merge-by-size ALWAYS qualifies on the size dimension; (3) `dashboard.rs:552` + `dashboard_web.html:368` have a `size_bytes || live_size` fallback that never triggers. NOT fixed alongside F-OVERVIEW-OPENTAIL on purpose: populating `size_bytes` with a real total would silently ACTIVATE size-based auto-policy on any cluster with an armed policy + `--dashboard-allow-mutations` (behavioral change ⇒ [[feedback_warn_on_backward_incompat]]); it needs its own decision on the intended semantic (LSM-resident per the stale doc, vs the total-footprint `open_tail_bytes + sealed_sum` that F-OVERVIEW-OPENTAIL now computes manager-side).
- **Decision (2026-07-05, user "fix this")**: semantic = **LSM-resident** (Σ SST `tables[].len` + active memtable + Σ imm memtables — the field's original doc intent AND the right signal for split/merge: logical data size, NOT total footprint incl. the transient log-stream WAL tail that GC reclaims). Deliberately DISTINCT from F-OVERVIEW-OPENTAIL's overview `live_size` (total extent footprint): e.g. part 17 = 21 MB LSM `size_bytes` vs 1.5 GB overview.
- **Scope**: `PartitionData::lsm_resident_bytes()` (lib.rs, local + cheap, no RPC — reads the module-private memtable `mem_bytes`); `background_maintenance_loop` stores it into `metrics.size_bytes` on the same throttled (30 s) refresh tick as the F-OVERVIEW-OPENTAIL open-tail probe (synchronous, no detach — local). Fixed the stale field doc. NO wire change (`size_bytes` already existed).
- **Policy-activation note ([[feedback_warn_on_backward_incompat]])**: size-based split/merge (`policy.rs`) now operates on REAL values instead of 0 — auto-actuates ONLY under an armed policy enabling split/merge (the `aggressive` preset). The running cluster's armed policy is `space-reclaim` (GC + EC only, no topology change), so no behavior change there unless the operator switches to `aggressive`.
- **Acceptance**: `size_bytes` non-zero in `autumn-op info --part --detail` + the `autumn_ps_partition_size_bytes` Prometheus gauge; distinct from the overview total footprint.
- **Status**: `passes: true` (2026-07-05) — PS builds clean, 0 new clippy. LIVE-VERIFIED after a PS restart (no wire change): `info --part 17 --detail` `size_bytes` `0 → 21242193` (~20 MB LSM data), while the overview still correctly shows 1.5 GB total footprint — the two measures are cleanly separated.

### F-DF-OPENTAIL — `autumn-op df` amplification must divide by the logical FOOTPRINT (sealed + open tail), not sealed-only
- **Trigger** (2026-07-05, user "amp 45.18x 放大45倍?"): `df` showed `amplification = physical_used / logical_stored_sealed = 45x` on a 3-replica cluster (should be ~3x). Root cause = the SAME open-tail asymmetry as F-OVERVIEW-OPENTAIL, in the capacity path: `physical_used` (Σ EN extent_bytes) INCLUDES open-tail bytes, but `logical_stored` only summed SEALED extents' `sealed_length`. A partition whose data lives in open tails (part 17: 1.6 GB open log holding LIVE large-value / VP bytes) contributes ~fully to the numerator and ~0 to the denominator → amp inflated ~15×. **Key correction (user)**: the open-tail log bytes are NOT "WAL debt" to be excluded — for a VP workload the large VALUE bytes live in `log_stream` (SST holds only pointers), so they are legitimate LIVE logical data that BELONGS in the denominator. (CoW does NOT affect this: both `physical_used` and `logical_stored` dedup shared extents — CoW only double-counts in the per-partition overview view.)
- **Scope**: (#1, correctness) `StreamClient::open_tail_committed_len` returns the tail's committed length ONLY when `!sealed` (a sealed tail is already in the manager sealed sum → double-count); the PS open-tail probe (F-OVERVIEW-OPENTAIL) uses it instead of `commit_length`. Fixes a double-count in the shipped overview too: a sealed-tail partition (CoW split child / just-reopened) over-reported (part 45 showed 147.6 MB vs true 94.1 MB). (#2, amp) `ClusterDfResp.logical_open_tail` (**WIRE v16**, fp `4c2dd28d4b3ff567`) = Σ PS-reported `open_tail_bytes` across partitions (refs=1 partition-private → simple sum, no CoW dedup); manager sums it each cluster-df tick from the policy window; `autumn-op df` + dashboard compute `logical_footprint = sealed + open_tail` and `amp = physical_used / footprint`; df prints the `sealed + open_tail = footprint` breakdown.
- **Acceptance**: amp ≈ replication factor (~3× for RF3, lower with EC); overview per-partition size == `info --part` EN-probe for sealed-tail partitions (no double-count); `writable_est` no longer crushed by a bogus amp.
- **Status**: `passes: true` (2026-07-05) — builds clean, 0 new clippy, rpc 44 wire tests green (v16 fp `4c2dd28d4b3ff567`). **LIVE-VERIFIED** after same-commit `cluster.sh restart 5`: `df` amp **45.18x → 3.00x** (physical 5.32 GB / footprint 1.77 GB = sealed 117 MB + open_tail 1.66 GB); WRITABLE(est) 11 GB → 155 GB; **overview now matches `info --part` to the byte for ALL partitions** (part 45 147.6 → 94.1 MB; 54/60/66 exact) — the #1 sealed-tail double-count is gone.

### F-DF-WALDEBT — accurate WAL-debt (dead-value) metric incl. open-tail discard [deferred]
- **Trigger** (2026-07-05, chosen option (b) during F-DF-OPENTAIL): operators want to see "how much of the log_stream is DEAD (overwritten/deleted large values) vs live" — the true space-reclaim signal. `gc_debt_bytes` already tracks reclaimable (dead) bytes on SEALED log extents, but the OPEN tail's dead bytes are NOT tracked. So a partition whose whole log is one big open tail (part 17: 1.6 GB open log, `gc_debt=0`, `sealed_log_extent_count=0`) shows "no debt" while its real dead fraction is unknown. NOTE: `footprint − size_bytes` is NOT the debt (rejected during F-DF-OPENTAIL) — `size_bytes` is SST-only and excludes the live VP value bytes in the log, so it would falsely flag a healthy VP partition as ~all-debt.
- **Scope (when triggered)**: PS tracks a discard/dead-byte estimate for the OPEN log tail (not just sealed extents' discard map), aggregate cluster-wide, surface in `df` as a dead-vs-live breakdown; decompose `physical/data = replication_amp × wal_debt_ratio`.
- **Acceptance**: `df` shows a dead-byte / reclaimable figure that includes open-tail dead values; part 17's real debt (not 0) is visible.
- **Status**: `passes: true` (2026-07-11, option-A ride-on-persisted-discard-maps). The dead-byte account is NOT a bespoke counter — it is DERIVED each PS GC tick from the already-persisted SST `MetaBlock.discard_count` maps (which `get_discards` aggregates and `valid_discard` filters to SEALED extents for `gc_debt`). The open-tail dead bytes are exactly the discard-map entry for the LAST (open) log extent that `valid_discard` drops. Impl: `PartitionMetrics.open_tail_dead_bytes` refreshed BEFORE the `<2`-extent gate in BOTH the GC-dispatch and the F203 periodic refresh paths (the headline all-open-tail case has a SINGLE log extent, so a gate-gated refresh would leave it 0 exactly where it matters), reusing one `get_discards` per tick; shipped via `PartitionLoad.open_tail_dead_bytes` (WIRE v17→**v18**, fp `dd40c423722d2a44`, same-commit); manager sums `Σ(gc_debt + open_tail_dead)` → `ClusterDfResp.logical_wal_debt`; `autumn-op df` prints `WAL debt: <bytes> dead (<pct>% of footprint, GC-reclaimable; incl. open-tail)` + `--json` `logical_wal_debt`/`wal_debt_ratio`; dashboard `/api` df parity; Prometheus `autumn_ps_partition_open_tail_dead_bytes` gauge. Survives restart exactly like `gc_debt` (rides the meta_stream checkpoint) with zero write-path cost. Verified: rpc 44 (v18 fp pinned) / PS 190 (+3 `background::wal_debt_tests`: last-extent extraction, disjoint-from-gc_debt no-double-count, zero-on-all-live/absent/negative) / manager 182 lib tests green; 0 new clippy; workspace+tests build clean. **coco findbugs (GPT-5.5, deep, 3 rounds): P1 + P2 FIXED, P3 declined.** P1 — the refresh sat AFTER the `<2`-extent gate so the all-open-tail (single-extent) headline case never updated it (fixed: hoist before the gate in BOTH GcRecv + GcTimeout). P2 — the `<2` early-exit left `gc_debt_bytes` stale, which the new manager sum would over-report as `logical_wal_debt` for a partition reclaimed down to one extent (fixed: store `gc_debt=0` on the no-sealed-prefix paths). P3 (declined) — cross-partition `.sum::<u64>()` overflow needs ~18 EB of dead data cluster-wide (physically impossible; sibling `logical_open_tail`/`logical_stored` sums are plain `.sum()` too; repo rule = no defensive fixes for imaginary bugs). NOTE (not covered, acceptable per the "estimate" scope): dead values OVERWRITTEN-BUT-NOT-YET-COMPACTED (old VP still live in memtable / an un-compacted SST) aren't in any discard map yet — compaction folds them in on its next pass; the figure converges monotonically. Live cross-host `df` verification (part-with-only-open-tail shows non-zero WAL debt) DEFERRED to a cluster run (multi-tenant box blocks local EN bring-up).

### F-FENCE-DRAIN — fence must drain open tails + hard placement exclusion (Fenced/Maintenance/Suspected)
- **Trigger** (2026-07-04, found live on the 8-EN test cluster; user: "这是一个设计阶段没想过的问题"): the F211 fence→recovery→remove decommission pipeline has a design blind spot never recorded or deferred anywhere (archive F211-A..I, ops.md, CLAUDE.md all silent): (1) recovery rebuilds ONLY sealed extents (`recovery.rs` dispatch pre-filter), so a fenced node's OPEN tail (an idle partition's log/row/meta tail) never drains — and `remove`'s precondition counts it as a blocking reference → remove never unblocks (observed: extents 70/74 stuck on fenced 56/58/60). (2) NO placement site consults `node_overrides` — fenced-but-alive nodes stay `Online` and keep receiving new extents (observed: fenced nodes' shard counts GREW 1→2/1→3 after fencing). (3) CLAUDE.md note 23's claimed "bump owner-lock revision on fence" was REMOVED by the BUG#3 Layer B fix — fence had ZERO write-path effect. (4) sealed-EMPTY extents (`sealed=true, sealed_length=0`) were also skipped by the `sealed_length==0` dispatch filter → same remove-blocker. User decisions: drain = **PS-driven roll** (manager-unilateral seal risks truncating acked data — EN `commit_length` is check-only, never raises the epoch floor, so a live writer keeps appending past a manager probe-seal; the safe unilateral variant needs an EN-side seal RPC → deferred follow-up F-FENCE-SEAL); placement exclusion = **Fenced + Maintenance + Suspected hard** (`Suspend` stays soft — bootstrap seeds every node Suspend). Dead-EN scenario explicitly in scope: F227 lenient seal + ≥1-reachable-source recovery cover it; all-replicas-unreachable must fail LOUD (Precondition), never silently seal.
- **Scope**: (A) `placement_excluded_node_ids()` (manager lib.rs; overrides Fenced|Maintenance ∪ `node_states.suspected_node_ids()`) threaded as a NEW `hard_excluded` param of `select_nodes` (filtered at the top: count-precheck + cold-leader fallback both inherit it; never backfilled, unlike the F190 soft exclude) + all 3 fallback walks (create_stream / alloc / merge P1.5) + `dispatch_recovery_task` target candidates + `handle_force_ec_convert` extra-parity pool. (B) `drain_fenced_open_tails` sweep in `recovery_dispatch_loop` (per tick; 30 s per-partition cooldown `roll_tails_cooldown`): OPEN tails (`!ex.sealed`) with a fenced member → resolve owning partition (streams→partitions→part_addrs, region/ps_nodes fallback; WARN when unresolvable) → **`MSG_ROLL_TAILS` (partition_rpc 0x57, WIRE v13 fp `87ad9d165bd07e15`, MIN=MAX=13 same-commit deploy)** with `(stream_id, expected_tail)` pairs → PS `handle_roll_tails` (spawned like SPLIT_PART): idempotency check (current tail == expected else skip), log/meta tails via P-log `part_sc.seal_and_roll_tail` (the WAL-self-heal primitive; F227 lenient probe seal), row tail via P-bulk's F255 barrier with new `RowInvalidateBarrierReq.seal_and_roll: true` (drain-inflight-to-zero then `bulk_sc.seal_and_roll_tail` — row single-writer invariant preserved; split keeps `false`). Once sealed → next recovery tick's fenced branch rebuilds → remove unblocks. (C) recovery dispatch pre-filter `sealed_length == 0` → `!ex.sealed` so sealed-empty extents rebuild (EN 0-byte copy works; P0-C sets the sealed flag). (D) docs: CLAUDE.md note 23 stale-claim fix + F-FENCE-DRAIN block; ops.md "Node decommission runbook" section.
- **Acceptance**: (a) unit — manager lib tests green incl. select_nodes exclusion; rpc wire tests green (v13 pinned). (b) live drain: on the 8-EN cluster with 56/58/60 already Fenced holding open tails 70/74, full stop → new binaries → start (etcd preserved): sweep rolls the tails within ~2 ticks WITHOUT client writes, recovery rebuilds, `info` shows 56/58/60 → 0 shards, `remove 56/58/60 --by op` all return ok. ### F-FENCE-SEAL — manager-unilateral open-tail seal (EN-side seal RPC) [deferred]
- **Trigger** (2026-07-04, recorded per house rule "v2 再做 must be a feature entry"): F-FENCE-DRAIN's PS-driven roll requires the partition to have a serving PS. A partition with NO PS (all PS down / unassigned for a long period) cannot drain its open tails; the sweep WARNs per cooldown. The WAS-native alternative — manager seals unilaterally — needs an EN-side seal RPC that persists the sealed flag in `.meta` and REJECTS subsequent appends (fencing the writer first), because EN `commit_length` is deliberately check-only (the "Layer-C poison" lesson): probe-sealing under a live writer would truncate acked data.
- **Scope (when triggered)**: EN `MSG_SEAL_EXTENT` (persist sealed in `.meta`, reject appends with a distinct code the writer's roll path maps to seal-and-roll), manager seal-over-reachable orchestration (seal at ENs FIRST, then min over responses, then persist), writer-side append-rejection → existing roll machinery.
- **Acceptance**: fence a node while its partition has no serving PS → tails still drain; live-writer race test proves no acked-data truncation.
- **Status**: `passes: false` (deferred — trigger condition not yet observed in practice; rebalancer reassigns partitions within seconds in all runs so far).

### F-DIRECT-MANY — batched client direct-read (fuse / kvcache / fsspec opt-in)
- **Trigger**: user 2026-07-07, continuing the "autumn-fuse 是否该默认 --direct-read" discussion. F259 `get_direct` only bypasses the PS for a SINGLE whole-value read; fuse/kvcache/fsspec read in BATCHES via `get_many_into` (PS-proxied `MSG_GET_ZC`), so large-file (model) serving never took the PS off the data path. User asked for a batched direct-read shared by all three frontends, and set two constraints: (1) direct-read is TOPOLOGY-dependent (needs the client to reach EN data ports) so each frontend needs its OWN opt-in flag, default OFF — never a hardcoded SDK default; (2) it must handle mixed-size batches (some values large, some small) correctly.
- **Scope**:
  - **PS sub-range redirect** (`partition-server/src/rpc_handlers.rs::get_value_inner`): `MSG_GET_REDIRECT` was whole-value-only (`req.offset==0 && req.length==0`); fuse whole-extent reads carry an explicit `length` so they never redirected. Now redirects any VP sub-range whose CLAMPED requested length `r_len = (length==0 ? vp.len-off : min(length, vp.len-off))` is ≥ 64 KiB, returning `value_offset = vp.offset + req.offset`, `value_len = r_len`. Single-key `get_direct` (0,0) is the `r_off==0, r_len==vp.len` special case — byte-identical. Sub-ranges past the value end (`req.offset > vp.len`) and sub-64 KiB requests fall through to the inline proxy resolve unchanged. No wire-struct change (only PS handler logic) → NO WIRE bump.
  - **Client `get_many_direct`** (`client/src/lib.rs`): dest-based batched direct-read mirroring `get_many_into`. Per item, `read_len ≥ 64 KiB` → `MSG_GET_REDIRECT` → descriptor → EN direct read (`read_extent_value_direct`, pooled `Bytes`) copied into `dest`; inline (`extent_id==0`, PS declined) copied straight in; ALL-replica failure → proxy `get_range_into` fallback. `read_len < 64 KiB` → plain proxy `get_range` + copy (mixed-size batches route per item). Extracted `read_redirect_replicas` (shared with `get_direct`) + `get_range_direct_into` (per-item core). The one extra copy vs `get_many_into`'s recv-into-dest is deliberate: the direct read carries a 3 s timeout + replica failover, which `call_into_dest`'s cancel-safety contract forbids, so it uses the pooled recv (`call_into_pooled`) then memcpys — the price of failover-safety on the bypass path.
  - **Frontend flags (now DEFAULT ON everywhere — 2026-07-09 user directive; topology-dependent, size-gated, fallback+warn make it safe)**: fuse `--direct-read` (default `true`; `--direct-read false` to disable) → `FsState.direct_read` → threaded into each `ReadPlan` → `read::execute` picks `get_many_direct` vs `get_many_into`; python `BatchClient(direct=True)` (PyO3 default stays `false`, but every consumer passes `True`) → Get arm chooses the primitive; `autumn.Fs.connect(..., direct_read=True)` → `FsState.direct_read` (fsspec `AutumnFileSystem(direct_read=True)`); kvcache `AutumnKVConnector` (`kv_connector_extra_config.direct_read`, default True → `_AutumnKVStore` → `BatchClient(direct=…)`); `autumn_vllm_loader` (`model_loader_extra_config.direct_read`, default True). **Requirement 2 (size-gated) already holds**: `get_many_direct` routes per item via `zc_worthwhile` — only ≥ 64 KiB reads issue `MSG_GET_REDIRECT`, < 64 KiB stay on the proxy. Safe even when ENs are unreachable — each item falls back to the PS proxy (authoritative); the shared client (`read_redirect_replicas`) logs ONE `WARN` (`DIRECT_FALLBACK_WARNED`) on first fallback so a wrong topology surfaces without per-read spam.
