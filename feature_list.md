### BUG-KVC-TENANT — kvcache tenant carries no model identity → cross-model KV aliasing (silent correctness bug)
- **Trigger** (2026-07-16, live VKE incident): Qwen2.5-7B-AWQ then Qwen2.5-32B-AWQ served with the SAME config via `autumn_vllm_loader` (config/tokenizer at the fixed local dir `/model-cfg`, weights streamed from autumn) → both landed in tenant `kvc/model-cfg_0_1/` (dump: one prefix hash with 28 layers among nine 64-layer ones). Same tokenizer ⇒ same token ids ⇒ same `prefix_hash` ⇒ 32B admitted 7B's presence markers and cross-read its KV. Bonus defect: the load-miss-after-marker warning blamed "possible TTL grace breach" unconditionally — misleading at `ttl_secs=0` where expiry is impossible.
- **Scope**: `python/autumn_kvcache` — new `_identity.py` (pure, offline-testable): `vllm_identity_sources(vllm_config)` extracts arch shape (layers/hidden/kv_heads/head/vocab/model_type/dtype/quant/MLA; field names verified against vLLM v0.23.0) + weights source (`load_format`, autumn loader's `model_loader_extra_config["path"]`) + optional `kv_connector_extra_config["model_id"]`; `fingerprint_from_sources` = canonical sorted `k=v` sha256 → 12 hex, deterministic cross-process; `tenant_cfg_from_vllm` (moved from vllm_connector, now also wires the previously-hardcoded-False `is_mla_model` from `ModelConfig.use_mla`). `build_tenant_suffix(cfg, model_fingerprint=None)` slots the fingerprint between model and tp/pp. vLLM connector: fingerprint REQUIRED (loud warning if underivable), identity sources logged at startup, miss-after-marker warning states plausible causes per TTL config (ttl=0 ⇒ tenant/model mismatch, never TTL). sglang backend: default tenant format UNCHANGED (model_name is a real identity there; no key invalidation), optional `extra_config["model_id"]` escape hatch. `__init__.py` → lazy re-exports (PEP 562) so `_keys`/`_identity` are importable without the `autumn` native module.
- **Acceptance**: offline unit tests (`tests/test_tenant_identity.py`, no cluster/engine/native module): 7B-vs-32B same-path ⇒ different tenants; every arch dimension + weights_path + model_id splits the tenant; same config ⇒ stable tenant with the exact canonicalisation PINNED (accidental fingerprint drift = fleet-wide cold cache); sglang legacy strings byte-identical; MLA/tp/pp semantics preserved. Cluster-required smoke/dataplane tests unchanged.
- **Residual (documented, NOT closed)**: same architecture + same weights-identity source — two finetunes loaded from the same local path with the default loader, or weights overwritten in place at one autumn path — still collide; mitigation = explicit `model_id` / new weights at a new path. Weights-content digest (e.g. safetensors header hash from the loader) evaluated as future work.

### BUG-MGR-RETRY-CLASS — code-classified manager-call retry + owner-fence self-heal (stale-epoch 45 s writes)
- **Trigger** (2026-07-16, live VKE incident): after a rebalance, a PS kept serving partition 17 with a permanently stale `owner_epoch` (manager expected 14396, client sent 14364 — 380 rejections over 20 min, number never changed). ### F-REGION-REBALANCE — active region→PS load rebalancing (manual `autumn-op rebalance` + auto-policy)
- **Trigger** (2026-07-15, live-cluster observation): after a rolling `kubectl apply` restart the VKE cluster had **all 32 partitions serving from one PS** (ps-2), ps-0/ps-1 idle. Root cause is `rebalance_regions` (manager lib.rs): the region→PS assignment is STICKY — it KEEPS a region on its currently-registered PS and only reassigns regions whose PS is UNREGISTERED. So an eviction window during a rolling restart piles every partition onto whichever PS was up, and NOTHING re-spreads them (a PS restart or manager restart both keep the sticky assignment; verified live — a parallel PS delete left all 32 on ps-2). The only non-destructive re-spread with pre-existing tooling was NONE (reset destroys data). Every reference system autumn is modeled on has an ACTIVE balancer: WAS Partition Manager, Bigtable/HBase `StochasticLoadBalancer`, TiKV/PD `balance-region`, Ceph balancer, `hdfs balancer`. autumn's `rebalance_regions` is only a failure-reassignment mechanism, not a load balancer — this closes that gap.
- **Design decisions**: (#1) the region-MOVE mechanism already exists (rewrite `MgrRegionInfo.ps_id` → PS `sync_regions_once` closes on the old PS / opens on the new; the eviction path uses it). `rg` unchanged ⇒ `region_epoch` NOT bumped (the key RANGE didn't move, only which PS serves it; clients re-resolve via the refreshed `part_addr`). (#2) COUNT-based balance for v1 (HBase `SimpleLoadBalancer`) — partition count is the coarse-but-robust signal; a req/s-weighted variant reuses the same apply path later. (#3) THROTTLED by `max_moves` because each move = a partition reopen on the target (seconds of that-partition unavailability, SDK retries absorb it) — like HBase limiting concurrent region moves; NOT free like Kafka leader election. (#4) autumn has ONE owner-PS per partition (replicas are in the stream/extent layer, fenced by owner_epoch) ⇒ only a `balance-region` dimension, NO `balance-leader` (simpler than TiKV/PD).
- **Scope (phased)**:
  - **Phase A — manual `autumn-op rebalance [MAX_MOVES]` DONE (2026-07-15).** `MSG_REBALANCE_REGIONS` (0x56) + `RebalanceRegionsReq{max_moves}` / `RebalanceMove{part_id,from_ps,to_ps}` / `RebalanceRegionsResp{code,message,moves,moved}`, **WIRE v21→v22** (fp `57fe8f244d8fd5c1`, same-commit deploy). Pure `AutumnManager::compute_rebalance_moves(state, max_moves)` (greedy most-loaded→least-loaded until max-min gap ≤ 1; deterministic — ties by lowest ps_id, moves the largest part_id; only REGISTERED PS participate). `handle_rebalance_regions` (leader-gated; apply in-memory then `mirror_partition_snapshot` — the eviction path's memory-first-then-mirror idiom). `ClusterClient::rebalance_regions`. `autumn-op rebalance` CLI (`[MAX_MOVES]` optional, 0/absent = balance fully; text + `--json`). 5 unit tests (`rebalance_*`: 32-on-one → gap≤1, max_moves cap, already-balanced no-op, deterministic dry-run, single-PS no-op).
  - **Phase B — auto-balance via dashboard policy CODE DONE (2026-07-15, WIRE v22→v23, fp 6b0224cb5e4f13f3).** `POLICY_KIND_REBALANCE=7` (append) + `policy_kind_names` row. `PolicyEngine::compute_rebalance_advisory(state, now)` — CLUSTER-level (one candidate/tick, primary=secondary=0), sourced from `regions`+`ps_nodes` (partition COUNT, not PartitionLoad); fires when per-PS spread > `rebalance_gap_threshold` (default 2, hysteresis) and outside `rebalance_cooldown_sec` (120s, via new `PolicyEngine.last_rebalance_at`); wired into `recompute_advisory_cache`. `actuate_candidate` REBALANCE arm → `handle_rebalance_regions(rebalance_max_moves_per_tick=4)` (bounded per-tick, gradual). auto_policy.rs: 6th switch `rebalance` (`kinds_from_switches` idx 5, `preset()` `[bool;6]`, `sanitize_entry` truncate/pad 6, `kind_priority` rebalance=1 after split, `policy_kind_str`/`describe_candidate`/`candidate_to_cmd` arms) — ON in `balanced`+`aggressive` presets, OFF elsewhere. dashboard.rs `switch_order`/`switches_to_dict`/upsert + dashboard_web.html toggle. 4 `rebalance_advisory_*` tests (fires-on-concentration, silent-when-balanced, respects-cooldown, disabled-when-threshold-0) + updated auto_policy switch tests. **Backward-compat**: `MgrAutoPolicyEntry.switches` is a variable-length `Vec<bool>` (rkyv layout UNCHANGED — adding a 6th element is a value not a layout change), so an old `autoPolicy/config` decodes cleanly under v23 and `sanitize_entry` pads to 6 (rebalance OFF); no etcd migration/reset. `PolicyConfig` (the 3 new rebalance thresholds) is in-memory (compiled defaults + runtime override), NOT persisted — same as every advisory threshold. LIVE deploy/validate pending.
- **Acceptance**: **Phase A** — 5 `rebalance_*` unit tests green; workspace + all test targets build clean; WIRE v22 registry test green; LIVE on VKE: `autumn-op rebalance` re-spreads the 32-on-one-PS cluster to ~11/11/10, `info` confirms, write/read stays green through the moves. **Phase B** — advisory fires on imbalance, armed controller converges a concentrated cluster gradually, dashboard switch toggles it, default-off preserved.

### F-SEALED-EMPTY-SWEEP — manager backstop sweep for leaked sealed-empty non-tail stream members
- **Trigger** (2026-07-14, BUG-FLUSH-TIMEOUT-LEAK follow-up): the live 5-node wedge (10.4 TB leaked / 222 GB logical, 47×) was fixed two ways in `crates/stream/src/client.rs` — size-scaled append deadlines (`effective_append_timeout`) and writer-side reclaim of a tail sealed at commit=0 on roll-away (`reclaim_abandoned_empty_tail`, best-effort punch). The reclaim is CLIENT-side and best-effort: if the punch (or the authoritative `extent_info` re-fetch) fails — manager briefly unreachable, extent momentarily in a Recovery/EC ledger op — or the writer process dies right after the roll, that one sealed-empty extent still leaks forever (same unreclaimable shape: `sealed=true, sealed_length=0`, refs≥1, non-tail stream member, referenced by no VP/SST/checkpoint, invisible to accounting, skipped by GC/truncate/orphan-reconcile). A cluster already poisoned by the pre-fix bug also holds ~40k such extents that the writer-side fix will never revisit.
- **Scope (when triggered)**: leader-only manager sweep (mirror `extent_both_zero_sweep_loop`, extent_delete.rs): for each stream, any member extent that is (a) NOT the tail (`extent_ids.last()`), (b) `sealed == true && sealed_length == 0` (authoritative empty seal — manager state note 32), and (c) not in the F207 inflight ledger → remove from `streams/<id>` membership (value-CAS per note 33) + refs-- (extent CAS) → existing pending-delete queue unlinks the physical files.
