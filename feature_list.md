### F-MEM-8 — CJK tokenization for the BM25 lexical leg
- **Trigger**: the tokenizer treated a CJK run (no whitespace boundaries) as ONE maximal-alphanumeric term, so `index_memory("我喜欢猫")` stored a single 4-char term and a query `猫` could never match. Chinese/Japanese/Korean agent memory was effectively unsearchable lexically.
- **Scope**: `recall.rs` — `is_cjk` (Han + kana + Hangul + CJK Ext A/B/C–F + compat) + tokenize emits each CJK codepoint as its own term (unigram), flushing any pending Latin run at the boundary; Latin runs keep lowercase + stopword + plural-fold. Unigram (not bigram) so single-character queries match and `doc_len` stays comparable across scripts (no length-norm skew); hybrid vector leg supplies phrase precision. Bigram = future refinement.
- **Acceptance**: unit test (`cjk_unigram_tokenization`: Chinese/Japanese/Korean split, mixed Latin+CJK, tf accumulation, kana-punctuation excluded, halfwidth katakana) + e2e against a live cluster (`猫` matches `我喜欢猫`, not `狗很可爱`, through the full posting path).
- **Status**: `passes: true` (completed 2026-06-30) — 20/20 unit tests; e2e exit 0 with the CJK case. coco review (GPT-5.5): P1 (upgrade-migration for old CJK indexes) N/A — autumn-memory is unreleased (no persisted index exists), and the index is a DERIVED artifact (doc/{id} keeps the original text → reindex is always possible, no data loss); P2 (kana block included punctuation/combining marks like `・` → bogus terms) FIXED by AND-ing `is_alphanumeric()` + tested; P3 (script-coverage gaps) FIXED — added Hangul Jamo/compat, katakana phonetic ext, halfwidth katakana, CJK compat supplement, Ext G/H + test; P3 (e2e cleanup) FIXED — zh1/zh2 now reaped.

### F-MEM-4 — vector-leg deletion / orphan-posting reaping (follow-up)
- **Trigger**: coco P2 (2026-06-30). `delete_memory` reaps the `doc/{id}` record + BM25 postings but NOT the IVF posting `ivf/{centroid}/{doc_id}` (the centroid isn't known at delete time). Orphan vectors then accumulate in IVF buckets: they waste storage, occupy `nprobe`/top-k slots, and add RRF noise to hybrid ranking. **Correctness is already safe** — the search boundary (F-MEM-3 `_resolve`, plan §8.5) drops any hit whose doc record is gone, so an orphan vector can never surface as a result; this is purely index hygiene/quality.
- **Scope**: O(1) reverse pointer `ivf_meta/vptr/{doc_id}` → centroid (4-byte BE), under `ivf_meta/` so it's outside the `ivf/` posting scan (train never mistakes it for a posting). Written by `index_vector` (which also reaps the old-bucket posting on a move → exactly one IVF copy per id), kept current by `train_centroids` re-bucket, read+deleted by `delete_vector`. `delete_memory` calls `delete_vector` unconditionally (a doc may be vector-only). KEY INSIGHT (refines the original deferral note): `train_centroids` re-buckets every posting it scans WITHOUT checking doc existence, so it NEVER reaps a deleted vector — the vptr reap is the only reaper, not a best-effort optimization. `_resolve` (F-MEM-3) remains the belt-and-suspenders correctness backstop for any expiry/in-flight race.
- **Acceptance**: after `delete_memory`, the deleted id no longer surfaces in `search_vector` (its IVF posting is gone) — verified e2e against a live cluster; `vptr` key is outside the `ivf/` scan range (unit).
- **Status**: `passes: true` (completed 2026-06-30) — e2e exit 0 (deleted d1 absent from vector search post-delete); 20/20 unit tests incl. the vptr-out-of-scan-range assertion. coco review (GPT-5.5): P2 (non-atomic `index_vector` — posting then vptr — could leave a vptr-less, unreapable orphan if the vptr write failed) FIXED by compensation (undo the posting + surface the error; only a double-fault leaks, still backstopped by `_resolve`). P1 (vptr-missing fallback for old data) N/A — unreleased, every posting now carries a vptr; a blanket `ivf/`-scan fallback was rejected because "vptr missing" is the NORMAL case for BM25-only docs, so it would make every vector-less delete O(N).
