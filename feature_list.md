### F-MEM-12 — recall P99 measurement + batched recall gets
- **Trigger**: plan §13 flags "先测 P99" — the recall/prefetch path is a keys-only posting scan + per-candidate doc point-get (the §14 two-hop), and its P99 decides whether memory recall can sit on the agent turn loop.
- **Measurement** (`python/autumn_memory/tests/bench_recall.py` + `run_recall_bench.sh`, 2000-doc single-agent corpus, realistic term-freq mix): the bench surfaced that `search_lexical` did a SEQUENTIAL per-candidate doc get (a common query term → ~900-long posting list → ~900 serial round-trips). **Release** recall P99 **≈18.5ms** (worst common-term ≈21ms) — fast enough for the turn loop. (Debug build was ~12× inflated, 231ms, all CPU — don't quote debug perf, per [[project_perf_baseline_storage]].)
- **Fix**: batch the candidate gets — `search_lexical`, `get_values` (episodic/replay), and `list_facts` now use `ClusterClient::get_many` (one `MSG_BATCH_GET` per owning partition; input-order preserved so episodic newest-first/chronological + fact key↔value pairing hold; per-key error still propagates). On loopback-release the win is modest (round-trips are cheap), but it's **essential cross-host**: O(candidates) sequential RTTs → one batch.
- **coco review (GPT-5.5)**: P2 (unbounded `get_many` over ALL candidates → one frame with every candidate body → OOM/frame-limit at scale, since BM25 has no early-termination) FIXED — `search_lexical` fetches in **bounded 256-candidate chunks** + a streaming top-k (memory + frame bounded; one RPC per chunk, not per doc); P99 23.5ms (vs 18.5 unbounded). P1 (`/tmp/*` glob guard bypassable by `/tmp/`, `/tmp/../x`) FIXED — `safe_tmp` requires `/tmp/<non-empty>` + rejects `..`. P3 (`BENCH_N`/`BENCH_Q`=0 div-zero) FIXED — validated > 0.
- **Acceptance**: `run_recall_bench.sh` green (P50/P90/P99 reported); 3/3 e2e + 20/20 unit tests confirm the batched/chunked paths preserve order/pairing/correctness.
- **Status**: `passes: true` (completed 2026-06-30) — **release recall P99 ≈23.5ms** single-term, **≈33ms multi-word** (4 terms, the realistic prefetch shape) at 2000 docs (chunked, scale-safe). Reproduce-first conclusion: recall is comfortably within the turn-loop budget, so concurrent per-term posting scans are NOT warranted (no measured need — would shave ~10ms off a 33ms P99 for added complexity). reconcile's audit gets left sequential (off hot path) — both noted as follow-ups only if a future workload measures a need.

### F-AUTHZ-1 — server-side data-plane key-range authorization (multi-tenant isolation)
- **Trigger**: plan §9.5 / §16 Phase 0 — the `mem/{tenant}/` prefix is ORGANIZATION, not security (a client can forge another tenant's prefix). User-directed (2026-06-30). Threat model (user): **trusted internal net** (defend rogue/buggy/test clients, NOT MITM, NOT compromised manager) → NO TLS.
- **DESIGN FINALIZED (2026-07-01, after multi-round user + coco discussion) — `docs/data_plane_authz_design.md` is the source of truth.** Architecture = **manager-as-KDC (issuance) + PS enforcement at the KV layer**, asymmetric **Ed25519** capability tokens:
  - **manager(leader) = KDC**: holds the signing PRIVATE key + a tenant account DB (etcd: `tenant → {credential_hash, allowed_prefixes}`); a client authenticates with a permanent tenant credential and gets a short-TTL signed capability token; supports auto-renewal (OAuth access+refresh / Ceph keyring+ticket pattern).
  - **PS = enforcement (KV layer)**: holds only the manager's PUBLIC key; `MSG_AUTH_HELLO` verifies the token signature ONCE per connection, binds `{allowed_prefixes, exp}`; every KV op does a byte `starts_with` + `exp` check; **NEVER calls the manager for enforcement** (data-plane independent of control plane).
  - token claims `{ver, typ, kid, iss, aud=cluster_id, nbf, exp, allowed_prefixes(each ends /)}`, canonical bytes + domain separation. Revocation = short TTL (prod hours) + kid rotation (emergency bulk) + stop-renewal (remove tenant → expires within TTL); no per-token deny-list. Perf: per-request ≈ ns (verify amortized to per-connection); only real cost = protected large-value reads via PS proxy (rare for agent-memory, optimizable via PS-minted EN-read-capability). EN direct-read bypass MUST be closed (descriptor is guessable coords, not a capability).
- **Superseded first attempt (REVERTED 2026-07-01)**: an earlier manager `token_hash→prefixes` registry that the PS would poll for per-request enforcement (etcd-RBAC-central-store shape) — user rejected ("auth 在 KV 层做"); code `git checkout`'d, wire back to v8. Distinct from the (unbuilt) admin-op auth `admin_auth_design.md` (Option A), which now protects the KDC's admin RPCs.
- **Stages (all TODO)**: **1 — KDC** (manager Ed25519 keypair + account DB + `tenant-create` admin RPC + `MINT_TOKEN` + `GET_AUTHZ_CONFIG`{pubkeys, protected}); **2 — PS enforce** (poll+cache config, AUTH_HELLO verify, choke points, Range whole-interval⊆prefix, batch per-op PermissionDenied, exp per-request, EN large-value via PS proxy); **3 — client + tooling** (SDK token + auto-renew + principal-partitioned conn pool, autumn-memory credential pass-through, `autumn-op gen-signing-key/tenant-create/mint-token`, cross-tenant e2e).
- **Status**: `passes: false` (design finalized; implementation not started; first attempt reverted).

### F-MEM-4 — vector-leg deletion / orphan-posting reaping (follow-up)
- **Trigger**: coco P2 (2026-06-30). `delete_memory` reaps the `doc/{id}` record + BM25 postings but NOT the IVF posting `ivf/{centroid}/{doc_id}` (the centroid isn't known at delete time). Orphan vectors then accumulate in IVF buckets: they waste storage, occupy `nprobe`/top-k slots, and add RRF noise to hybrid ranking. **Correctness is already safe** — the search boundary (F-MEM-3 `_resolve`, plan §8.5) drops any hit whose doc record is gone, so an orphan vector can never surface as a result; this is purely index hygiene/quality.
- **Scope**: O(1) reverse pointer `ivf_meta/vptr/{doc_id}` → centroid (4-byte BE), under `ivf_meta/` so it's outside the `ivf/` posting scan (train never mistakes it for a posting). Written by `index_vector` (which also reaps the old-bucket posting on a move → exactly one IVF copy per id), kept current by `train_centroids` re-bucket, read+deleted by `delete_vector`. `delete_memory` calls `delete_vector` unconditionally (a doc may be vector-only). KEY INSIGHT (refines the original deferral note): `train_centroids` re-buckets every posting it scans WITHOUT checking doc existence, so it NEVER reaps a deleted vector — the vptr reap is the only reaper, not a best-effort optimization. `_resolve` (F-MEM-3) remains the belt-and-suspenders correctness backstop for any expiry/in-flight race.
- **Acceptance**: after `delete_memory`, the deleted id no longer surfaces in `search_vector` (its IVF posting is gone) — verified e2e against a live cluster; `vptr` key is outside the `ivf/` scan range (unit).
- **Status**: `passes: true` (completed 2026-06-30) — e2e exit 0 (deleted d1 absent from vector search post-delete); 20/20 unit tests incl. the vptr-out-of-scan-range assertion. coco review (GPT-5.5): P2 (non-atomic `index_vector` — posting then vptr — could leave a vptr-less, unreapable orphan if the vptr write failed) FIXED by compensation (undo the posting + surface the error; only a double-fault leaks, still backstopped by `_resolve`). P1 (vptr-missing fallback for old data) N/A — unreleased, every posting now carries a vptr; a blanket `ivf/`-scan fallback was rejected because "vptr missing" is the NORMAL case for BM25-only docs, so it would make every vector-less delete O(N).
