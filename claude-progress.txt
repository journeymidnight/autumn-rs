Task scope: F170 — Close the last big inline-CPU offender on the EC
            read path. `ec_slice_decoded` was called inline on the
            compio runtime AFTER `spawn_blocking(ec_decode)` returns
            and unconditionally `.to_vec()`'d the full decoded
            payload — 50-100 ms of memcpy on a 256 MiB extent.
            Changed to take Vec<u8> by value; full-read branch now
            returns the input Vec via ownership transfer (zero copy).

Why:
  Continued thread-per-core audit prompted by user concern about
  GC pressure → compio block → heartbeat loss. Per F117 + the
  partition-server CLAUDE.md note 17 ("CPU-bound work MUST run on
  the blocking pool, not the compio event loop") any payload-sized
  memcpy on the compio runtime is a violation.

  F168 + F169 closed compaction's merge-loop and chunk-emit. F170
  catches the structurally-separate EC read sibling on the same
  principle:
    - `ec_decode` (RS GF(256), 100-300 ms): already in spawn_blocking
      via F117 (`crates/stream/src/client.rs:2069`).
    - `ec_slice_decoded` full-read (50-100 ms memcpy): inline on the
      compio runtime — fixed in F170 by zero-copy ownership transfer.
    - `ec_slice_decoded` sub-range (~ms): kept inline; spawn_blocking
      join overhead would dominate the actual work.

How:
  Pre-F170 signature:
    fn ec_slice_decoded(full_payload: &[u8], offset: u32, length: u32)
        -> Result<Vec<u8>>

  Post-F170 signature:
    fn ec_slice_decoded(full_payload: Vec<u8>, offset: u32, length: u32)
        -> Result<Vec<u8>>

  Full-read fast path: `if offset == 0 && length == 0 { return Ok(full_payload); }`
  — strictly zero allocation. The caller at `client.rs:1967`
  already owned the Vec returned from `ec_read_full`, so the move
  semantics drop in cleanly.

  New test `slice_full_read_is_zero_copy` asserts
  `out.as_ptr() == in_ptr && out.capacity() == in_cap`. Future
  refactors that reintroduce a memcpy will fail the invariant.
