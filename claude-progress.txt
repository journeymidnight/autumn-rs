Task scope: F-lease-preempt — force-revoke / writer revoke
  protocol. Phase 3 of docs/autumn_fs_lease_plan.md, the LAST
  piece of the inode-lease feature series. All three plan phases
  now landed.

  AcquireLease(force=true) against a held writer:
  - first call → manager pushes WillRevokeIn{grace_ms} to the
    current writer + returns RevokePending{eta_ms}.
  - retries before grace expires → still RevokePending with the
    remaining eta.
  - writer voluntarily releases → next acquire = Granted cleanly.
  - past the grace deadline → force-revoke (bump version, push
    LeaseRevoked to deposed writer + readers) + Granted.

  Same shape as NFSv4 delegation recall but driven from the
  client side via the existing long-poll invalidation channel —
  no new wire RPC.

  Not yet implemented (deliberately deferred, NOT blocking
  Phase 3 close):
    - Writer-side AUTO-flush + AUTO-release on receiving
      WillRevokeIn. Today daemon + fuse poll loops just log the
      WillRevokeIn event at WARN with the grace ms. The operator
      (or a higher layer) must react before the grace expires;
      the manager force-revokes after the deadline regardless,
      so correctness is preserved. Wiring auto-flush needs:
      * autumn-fuse: send a synthetic FsRequest::Flush + then
        the equivalent of FsRequest::Release for the affected
        inode from inside the poll loop's per-event handler.
        The compio thread already owns FsState so this is just
        a state mutation + lease::release call; the tricky part
        is the user-visible fd lifetime (the kernel still has
        the fd open — we'd need notify_inval_inode to drop the
        cache + accept that future ops on that fd return EIO).
      * autumn-ioring: walk held_leases for the matching ino,
        send the same "release-and-EBADF-future-ops" sequence.
      Tractable as a follow-up. The current design is correct
      (no data loss; just a 5s window where the preempter waits)
      and matches the plan's word-for-word "writer revoke 协议".

=== WHAT THIS COMMIT SHIPS ===

  Wire (same-commit deploy, per repo convention):
    AcquireLeaseReq gains `force: bool`.
    New CODE_REVOKE_PENDING = 6 (manager packs `eta_ms` into
    the response's `lease.ttl_secs` field — documented on the
    const, repurposed only for this code path).
    New LEASE_INVAL_WILL_REVOKE_IN = 4 invalidation kind. The
    `MgrInvalidation.version` field is repurposed to carry the
    grace milliseconds (also documented on the const).

  Manager state machine (crates/manager/src/inode_lease.rs):
    InodeLeaseState.pending_revoke_at: Option<Instant>.
    LeaseRegistry.revoke_grace: Duration (default 5s,
    DEFAULT_REVOKE_GRACE; `with_ttl_and_revoke_grace` lets
    tests use sub-second windows).
    New acquire_with_force(client, ino, mode, force, now):
      - force=false: identical to legacy acquire.
      - force=true + no current writer (or same writer): grant.
      - force=true + different writer + pending_revoke_at is
        None: set to now+grace, push WillRevokeIn, return
        RevokePending{eta_ms}.
      - force=true + different writer + grace > now: return
        RevokePending{remaining eta_ms}.
      - force=true + different writer + grace ≤ now: force-
        revoke (clear writer, bump version, push LeaseRevoked
        to deposed + readers), grant new acquirer.
    Legacy acquire(...) keeps its signature — delegates to
    acquire_with_force(.., force=false).
    release/tick/revert clear pending_revoke_at on writer-
    departure paths so a future force-acquire starts fresh.

  Six unit tests in inode_lease::tests covering:
    - force on held writer → RevokePending + WillRevokeIn push.
    - force retry before grace → remaining-eta math.
    - voluntary release within grace → next acquire Granted.
    - grace expiry → force-revoke + LeaseRevoked to deposed+
      readers + Granted to new acquirer.
    - force on no writer = just a grant.
    - force by self = idempotent refresh (no self-push).

  Client (crates/client/src/lease.rs):
    AcquireResult::RevokePending{eta_ms, manager_message}.
    acquire_force(cluster, client, ino, mode) — force=true
    variant, returns RevokePending on first hit.
    acquire_with_preempt_wait(cluster, client, ino, mode,
    max_wait_ms) — convenience loop that polls acquire_force
    with sliding backoff (50-500ms per poll) bounded by
    max_wait_ms. Returns the final outcome.

  Manager handler:
    handle_acquire_lease threads req.force → acquire_with_force.
    New RevokePending arm returns CODE_REVOKE_PENDING + packs
    eta_ms into lease.ttl_secs.

  Daemon + fuse update sites:
    ioring daemon's Open arm + fuse's Open + Create arms get a
    defensive `RevokePending => Err("BUG")` arm. These paths
    use non-force acquire so the variant is unreachable; the
    explicit arm makes a future refactor that flips them to
    force=true fail loudly instead of silently dropping the
    retry loop.
    ioring poll loop's per-event match: new
    LEASE_INVAL_WILL_REVOKE_IN arm logs at WARN with the
    grace ms so the operator can react.

  Integration tests (crates/manager/tests/f_lease_preempt.rs):
    Four tests against the real manager RPC:
      1. force_acquire_pushes_will_revoke_to_current_writer.
      2. voluntary_release_within_grace_lets_preempter_acquire_cleanly.
      3. force_acquire_after_grace_expiry_forces_revoke_and_grants.
      4. force_acquire_on_no_writer_grants_immediately.
    All 4 pass; #3 uses acquire_with_preempt_wait with 8s
    budget and exercises the full 5s grace + force-revoke +
    LeaseRevoked round-trip.
