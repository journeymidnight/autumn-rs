TaskStatus: completed
Task scope: F155 — rkyv checked decode (replaces `from_bytes_unchecked` with
            `from_bytes`). Closes the verified UB-on-malformed-input hazard
            in both `rkyv_decode` helpers (`crates/rpc/src/manager_rpc.rs`
            + `crates/stream/src/extent_rpc.rs`).

Why:
  Both rkyv_decode helpers used `unsafe { rkyv::from_bytes_unchecked }`
  with the comment "we control both sides" as the only safety
  justification. The unchecked path performs zero-copy deserialisation
  without any validation:
    - no bounds check on length-prefixed containers (Vec / String)
    - no pointer-relativity check on archived offsets
    - no sum-type discriminant validation
    - no alignment check
  Any malformed input triggers UB:
    - cosmic-ray bit flip past TCP's 16-bit CRC
    - struct-layout mismatch from a partial rolling upgrade
      (cf. F118 renamed MgrExtentInfo.original_replicates → ec_converted
       with no schema-version prefix to detect mixed-version peers)
    - in a future where the wire crosses untrusted boundaries, a hostile
      sender
  → out-of-bounds reads, pointer dereferences into arbitrary memory, or
  silent partial decoding into a corrupt struct that downstream code
  trusts (e.g. crashing the partition thread, or — worse — silently
  routing data to the wrong partition).

How:
  Switched both helpers to `rkyv::from_bytes::<T, RkyvError>(&v)`, the
  checked path. Added bound:
    T::Archived: for<'a> rkyv::bytecheck::CheckBytes<HighValidator<'a, RkyvError>>
  rkyv 0.8's `#[derive(Archive)]` auto-derives CheckBytes for the
  archived type, so all wire structs across manager_rpc.rs /
  partition_rpc.rs / extent_rpc.rs / etc. compile without further
  changes. The validator runs bytecheck's archive-validation pass before
  deserialising; malformed input returns clean `Err` instead of UB.

Cost:
  Validation adds a constant-overhead pass over the archived bytes. For
  the 4 KB hot path Put/Get this is a few µs per request — bounded and
  predictable. Perf-check on tmpfs post-F155 fluctuates 42k-102k ops/s
  across 6 runs (high rig noise on shared box), median within the
  F148-F150 baseline band (90-97k). No clean regression signal.

Out of scope (still deferred):
  - Wire-format schema versioning. F155 closes the UB-on-malformed
    input class of bugs; it does NOT close the rolling-upgrade-with-
    incompatible-schema class. A future feature could add a 1-byte
    schema_version prefix to every wire payload + a version-mismatch
    handshake on connect, so rolling upgrades fail loud at the wire
    boundary instead of silently decoding into a wrong struct (the
    failure mode F118's rename would have produced if anyone had
    attempted a rolling upgrade across that commit). Today's deployment
    model is restart-all-together, so version mismatch is
    operationally avoided.
