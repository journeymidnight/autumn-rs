Root cause (in code, pre-F141):
  crates/partition-server/src/background.rs::process_gc_chunk re-appended
  every still-live VP record one at a time:
      part_sc.append(log_stream_id, &log_entry, /*must_sync=*/true).await
  At 4 KiB-typical VPs over a 1–2 GiB sealed extent that's 64 k–256 k
  individual fsyncs × 3-replica fanout. The StreamClient per-stream worker
  mpsc and the extent-node WAL fsync rate ceiling pinned together at the
  same time, so foreground put traffic could not progress.

Completed (the four mitigations the user asked for; lands as a single feature):
  - feature_list.md: F141 entry added (passes:true) under the F140 section,
    with full mechanism, fix breakdown, env tunables, and verification.

  - crates/partition-server/src/background.rs:
      • New `GcWriteBatch { segments, pending, bytes, record_cap, byte_cap }`
        accumulates rewrites across `process_gc_chunk` calls (carries across
        chunks; flushes mid-chunk when full).
      • New `GcRateLimiter` (1-second sliding window) caps GC's
        log_stream throughput at AUTUMN_PS_GC_RATE_BYTES_PER_SEC bytes/s
        (default 64 MiB/s, 0 = unlimited).
      • New `gc_yield_now()` (one-shot Pending+wake) yields the compio
        scheduler to merged_partition_loop / ps-conn between batches.
      • New `flush_gc_batch(part, log_stream_id, part_sc, batch, must_sync,
        rate_limiter, moved)`:
          - Calls `part_sc.append_segments(log_stream_id, segments, must_sync)`
            ONCE per batch (was N times per record).
          - Walks the returned tail offset to compute per-record VP offsets,
            then `p.active.insert_batch(items)` — single RwLock acquire for
            up to record_cap inserts.
          - Updates `vp_extent_id`/`vp_offset` to the batch's `result.end`.
          - `gc_yield_now().await` then optional sleep on the rate budget.
      • Rewrote `run_gc`: holds `batch` + `rate_limiter` across the chunk
        loop, calls `flush_gc_batch(..., must_sync=false, ...)` mid-loop on
        cap, and ONE final `flush_gc_batch(..., must_sync=true, ...)` after
        the carry check before `punch_holes`. POSIX fsync semantics flush
        every prior must_sync=false byte on the same fd, so durability
        before the source extent is reaped is preserved with a single
        fsync per GC'd extent (was 64 k–256 k).
      • Rewrote `process_gc_chunk`: takes `&mut GcWriteBatch` and `&mut
        GcRateLimiter`; under a brief borrow_mut bumps `seq_number` +
        encodes the internal_key, builds (header_segment, value_segment)
        Bytes pairs into the batch, then `if batch.is_full()` calls
        `flush_gc_batch(..., must_sync=false, ...)`. WAL header op preserves
        original GC behaviour (`op = 1`, no VP flag — recovery's
        `value.len() > VALUE_THROTTLE` fallback at lib.rs:2891 still
        recognises the entry as a VP on replay because GC only ever
        rewrites entries that were tagged VP in the source extent).
      • New env knobs (all clamped, with sane defaults):
          AUTUMN_PS_GC_BATCH_RECORDS  ([1, 4096], default 256)
          AUTUMN_PS_GC_BATCH_BYTES    ([64 KiB, 256 MiB], default 4 MiB)
          AUTUMN_PS_GC_RATE_BYTES_PER_SEC (default 64 MiB/s, 0 = unlimited)
          AUTUMN_PS_GC_READ_CHUNK_BYTES   (default 8 MiB, was 64 MiB pre-F141)

  - Read-side follow-up (after live ps.log verification 06:08–06:11Z):
    The first-pass batching/sync fix collapsed GC writes to one batch
    per extent (`moved 23 entries` / `moved 91 entries`), but the user
    still observed `replica 0 rpc error: 127.0.0.1:9101 append timeout
    after 5s` on stream_id=26 / stream_id=33 (foreground log_streams
    of partitions 29 / 36). The PS-side trace showed a 17–21 s gap on
    extent-node 1's append-summary log line during a GC run on extent
    20 (sealed_length=1.09 GiB, EC-converted at eversion=3) — a single
    64 MiB EC subrange read was head-of-line-blocking the extent-node
    runtime long enough that foreground appends timed out at the
    StreamClient's 5 s ceiling. Two extra changes folded into F141:
      • `gc_read_chunk_bytes()` default lowered 64 MiB → 8 MiB.
      • After every `read_bytes_from_extent` in `run_gc`, call
        `gc_yield_now().await` and bill the chunk's bytes against the
        SAME rate limiter the writes use, so the 64 MiB/s budget
        bounds GC's TOTAL log-layer footprint (reads + writes).
