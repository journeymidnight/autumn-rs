Task scope: F139 — Extent-node delete vs in-flight recovery (orphan + write-to-unlinked-inode race).

Root cause (confirmed):
  Two reachable race subwindows between handle_delete_extent and run_recovery_task
  on the same extent_id:
  (a) Resurrection: ensure_extent auto-creates with create:true after delete
      unlinks the file → orphan on disk, no manager record.
  (b) Write-to-unlinked-inode: recovery holds Rc<ExtentEntry>; delete unlinks
      the path; recovery's pwrite succeeds on unlinked inode; data evaporates
      on fd drop. apply_recovery_done's None-branch silently Ok(())'d the stale
      task, masking the corruption.

Fix (symmetric in-flight-set pattern from F138):
  1. recovery.rs dispatch_recovery_task: skip dispatch when extent is in
     pending_extent_deletes — next 2 s tick naturally finds extent gone.
  2. rpc_handlers.rs handle_stream_punch_holes: return Err(Precondition) if
     any refs→0 extent is in recovery_tasks. PS GC retry backs off.
  3. rpc_handlers.rs handle_truncate: symmetric guard to (2).
  4. recovery.rs apply_recovery_done None-branch: enqueue PendingDelete for
     recovering node — immediate reap instead of 5-min orphan-reconcile wait.
  5. extent_node.rs handle_delete_extent: return CODE_PRECONDITION when
     recovery_inflight.contains_key(&extent_id). extent_delete_loop retries
     up to 60 × 2 s = 2 min budget.

Belt-and-braces: both manager and extent-node sides independently refuse,
covering leader failover where pending_extent_deletes is lost in-memory
but recovery_inflight survives on the extent-node process.
