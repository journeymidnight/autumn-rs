【2. split 判据重设计 —— 这是本轮的主体】
  现象（用户截图）：part 32 携带 73.8G、9 个 extent，但 row 只有 797.8K、
  live size 624.8K、0 iops、0 B/s，策略每个窗口发一次
  `split part 32  size>53687091200 (est_live 73 GiB, lsm 0 MiB)`。
  **判据错在把"携带字节"当成 split 的触发器。** split 切的是 key range，跟着 key
  range 走的只有 LSM；大 value 躺在 log_stream 里，CoW split 之后两个孩子**指着
  同一批 extent**，不 major compact 根本分不开。所以对这种分区，split 买不到任何
  东西，只买到一笔 compaction 账单 —— 而那正是它每个窗口在建议的事。
  改法（`crates/manager/src/policy.rs`）：
  - **一条 split 建议必须点名一个 split 能缓解的瓶颈**，只有三个，各有各的度量：
    请求率（一分区=一个 P-log 线程，~30K ops/s → `req_per_sec`）、
    字节率（一分区=一条 log_stream，~350 MB/s → `write+read_bytes_per_sec`）、
    LSM 大小（compaction/memtable 的工作量，也正是切一刀真能减半的那部分 →
    `size_bytes`）。
  - `SPLIT_SIZE_HARD` → `SPLIT_LSM_HARD`，**阈值 50 GiB 一个字节没动**，只把它量的
    东西从 `effective_size_bytes`（含 payload）换回 `size_bytes`（LSM 常驻）。
    小 value 负载两个度量本来就重合，所以那类负载的行为**逐位不变**，只有 VP 的
    假阳性消失。
  - 新增 `SPLIT_BW_HIGH` = 175 MiB/s（实测单 log_stream 天花板 ~350MB/s 的一半，
    跟 QPS 阈值取"用掉一半预算"是同一条规则）。这条以前**完全没人看** ——
    `write_bytes_per_sec`/`read_bytes_per_sec` 收上来了但没有任何判据消费它，
    而 1400 ops/s × 1 MiB 对 `SPLIT_QPS_HIGH` 来说是空闲，对那条流来说是打满。
  - 携带字节保留它真正答得好的两个问题：速率触发器下面的**地板**
    （`SPLIT_SIZE_MIN`，太小的不值得切）和 merge 的**否决**（两个胖分区不能并成
    一个）。`PolicyCandidate.size_bytes` 仍然报携带字节（"它有多大"就是含 payload 的）。
  - merge 的 cold 判定补上 `MERGE_BW_LOW`（= SPLIT_BW_HIGH/10，与 QPS 同样的 10×
    迟滞）：只看 QPS 会把 1.4 GB/s 的一对判成冷。
  - `HOT_COLD_MIN_HOT_SIZE_BYTES` 原本写成 `SPLIT_SIZE_HARD/2`；它量的是携带字节，
    从一个量 LSM 的阈值推导是范畴错误，改成独立的 25 GiB（值不变）。

【3. split/merge 前先 compact —— 原来没做，现在做了】
  PS 侧 `handle_split_part` 在 `has_overlap != 0` 时直接拒（`cannot split:
  partition has overlapping keys`），而 manager **看不见这个标志**，于是策略每个
  窗口发一次必被拒的 split。（2026-09-10 修过"被拒也进冷却"，那是限流，不是收敛。）
  - wire 加 `PartitionLoad.has_overlap`。**刻意没有**用现成的
    `sst_out_of_range_bytes > 0` 去推断：那是越界记录的**字节数**，一个 has_overlap=1
    而共享表里恰好没有越界 key 的分区它读 0 —— 正是会被放行的那一种。
  - PS 侧 `PartitionMetrics.has_overlap` 做跨线程镜像，`PartitionData::set_has_overlap`
    是**唯一写者**（Cell 在分区线程上，report_load_loop 在主线程只够得着 metrics）。

    `POLICY_KIND_MAJOR_COMPACT`，reason 写明它在给谁让路；受 `compact_inflight` 与
    `compact_cooldown_sec` 两道闸门约束。overlap 清掉后下一个 tick 拓扑动作自己回来。
  - 诚实地写在注释和文档里：若某个策略开了 split 却关了 compact，这条候选会被
    `kinds_from_switches` 滤掉、**什么都不会发生**。那是对的结果，而且是**看得见的**
    结果，不像原来的拒绝循环。（预置策略里只有 aggressive 开 split，它 compact 也开。）

【机制(评审纠正了我第一版的说法)】
  没有任何东西"把 commit 归零"——零从来没被覆盖过。新 worker 出生即 cursor=0,
  而唯一会把 cursor 抬到已提交长度的 SeedCursor 就在被跳过的那次初始化里。
    split → invalidate_stream(清 worker + 标记) → append spawn worker#2,初始化完成
    → worker#1 这才排空退出,按 key 删掉了 #2 的条目
    → 下次 append spawn #3,看到标记仍为 true 就跳过初始化
    → 第一个 append 报 "no tail set" → 被当软错误重载 tail → 重试在 cursor 0 处 lease
    → header.commit=0 → 每个副本照做,截断。

【修法】
  - 每个 worker 带 generation,两处删除都以它为门。
  - 顺序是承重的:把"清标记"挪到 generation 检查之前,所有显而易见的测试仍然全绿,
    但会让一个活着的 worker 在自己脚下重新初始化——两个 worker 用各自的 cursor
    写同一个 extent,比原 bug 更糟。已用测试钉死这个顺序。
  - "no tail set" 改为 fail-fast,不再软重试:下次再出生命周期 bug 会报错而不是截断。

【为什么这件事值得做:今天的盘级代码从没进过 chaos】
  harness 给每个 EN 只有一个 `--data` 目录。于是 9 月 9-10 号做的三件事 ——
  节点/盘两级放置(`choose_disk`)、坏盘触发重建、盘错误分类 —— 全部只有单测,
  一次都没在 nemesis 下跑过。"一台机器有多块盘"是 EN 自己划的界,
  harness 不划这条界,那条界后面的代码就永远不会被踩到。

【改法】
  `EnProcess.data_dir: PathBuf` → `data_dirs: Vec<PathBuf>`;每个 EN 一个 tempdir,
  里面 `disk{k}` 子目录当独立盘;`autumn-op format d0 d1 ...` 一次注册全部
  (它往每个目录都写同一个 node_id,所以 sentinel 读 `data_dirs[0]` 即可);
  EN 用 `--data d0,d1` 起。`find_extent_dat` 改成搜该节点的每一块盘 ——
  extent 落在哪块盘是节点自己的选择,harness 不能假设。
  旋钮 `AUTUMN_CHAOS_DISKS_PER_EN`(默认 2,`.max(1)`),设成 1 就能和单盘形态做 A/B。

【测出来的第一个:harness 自己的假阳性】
  seed 583 多盘跑失败,报"extent 25 在 node 16 上被腐化,它自己的节点 180 秒内
  从没说过,读会从这份坏副本上返回"。真相在 EN 日志里:
  `delete_extent: unlinked .dat + .meta extent_id=25` —— GC 在 scrub 走到 block 0
  之前就把这个 extent 回收了。**断言在要求一份已经不存在的字节被发现。**
  修法:注入时记下 `.dat` 路径和写进去的那 64 字节;验证时**先查日志**
  (所以"报了然后被删"仍算发现),再把剩下的分成"坏字节还在"(真发现)
  和"坏字节没了"(大声说明这次注入什么都没测到)。
  同一 seed 重跑,新分支如期命中并通过。

【测出来的第二个:recovery 的 op 台账永远停在 running(真 bug,已修)】
  同一轮还报 `op ... kind=8 target=0/20 still ACTIVE (state=1) after quiesce`。
  `note_recovery_dispatch` 每个 extent 只开一条台账、且只**复用**活着的那条;
  而 `apply_recovery_done` 有**五个**出口既不应用重建、也不留下任何还会再报的人:
    - EchoOfAppliedWork(重建早已落地,这是重发回声)
    - ReleasedAttempt(marker 被释放而执行者还在干)
    - 目标已在别的 slot(EC 转换中途改了布局)
    - replace_id 已不在该 extent
    - extent 在重建落地前被删
  五条全部把台账留在 RUNNING,而 `sweep_running_ttl` 按设计只收
  COMPACT/GC/FORCE_GC —— recovery 只要修复还没完成就该一直重试,不能按时间收。
  于是 `ops status` 对一个早已结束的 recovery 永远回答"running"。
  修:回声 → `complete_recovery`(SUCCEEDED,它描述的活确实成了);
  其余四条 → 新的 `abandon_recovery_entry`(FAILED + 原因)。
  **刻意不动的两条**:EC 转换在飞时的 defer、以及 DifferentAssignment ——
  这两条都留着一个活 marker,它自己的执行者还会来报。
  消融:把 recovery.rs 存起来跑新测试,五条出口**全部**报 `state=1`;
  加回修复,五条各自到达预期终态。

【测出来的第三个:rot 覆盖率断言把两种原因混成一种(harness,已修)】
  旧断言是"CorruptReplica 被选中却一次都没注入 ⇒ 本轮失败"。但同一个文件自己写着
  "a decline is per-tick, one round proves nothing" —— 两句话互相矛盾。
  拆成两种原因:`rottable_replicas` 现在返回 `RotTargets { ready, reachable }`,
  `reachable` 数的是"sealed + 多副本 + **至少有一个活着、没被 fence、没被隔离的持有者**"。
  reachable>0 而一次都没注入 = 有可注入的目标却没有任何节点 describe 过它 ⇒ 真失败;
  reachable==0 = 这一轮根本没有可用目标 ⇒ 大声记一笔,不判失败。
  **我第一版是错的,而且是同一类错**:只数了 sealed 的形状,没过滤持有者是否可达 ——
  那会在"唯一那个 sealed extent 的副本当时全被 fence 了"的轮次里去指控产品。
  是换了更细的仪器之后自己看出来的(第一版重跑 seed 66 报"1 个 sealed 可用",
  加上可达性过滤后 seed 66 直接过了)。
