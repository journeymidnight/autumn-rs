Task scope: F144 — Allocator node-selection bias. User observed that
            on a 4-extent-node cluster (node_ids 1, 3, 5, 7) every
            new stream / extent landed on [1, 3, 5]; out of 14 live
            extents only 2 ever included node 7. All replica reads,
            writes, and EC parity work concentrated on three of the
            four nodes. User confirmed root cause is allocator bias
            (not read load balancing) and chose option 2 from the
            design discussion: random shuffle replacing the existing
            "sort by node_id then take(count)" selection.

Diagnosis (full chain, captured in feature_list.md F144):
  • `AutumnManager::select_nodes` (crates/manager/src/lib.rs:597)
    collected nodes into a Vec, sorted ascending by `node_id`, and
    returned `take(count)`. With a sorted candidate list the lowest
    `count` IDs always win; node 7 was only ever selected when one
    of {1,3,5} was filtered out by the F121 online-disk check.
  • Two adjacent paths reproduced the same bug shape:
    - `recovery.rs:591-622` (EC-conversion extra-parity selection):
      walked `HashMap.values().take(extra_needed)`. HashMap order is
      formally undefined but deterministic per process, biased
      toward whichever node_id happened to be visited first.
    - `rpc_handlers.rs:845-851` (`handle_stream_alloc_extent`
      fall-back): sorted leftover candidates by `node_id` before
      walking, so a failed primary always retried on the
      next-lowest ID.
  • Compounding effect: an extent allocated as [1,3,5] then needing
    EC conversion to 3+1 picked node 7 as the only remaining
    candidate, so node 7 became the *parity* node almost
    exclusively — additionally lopsided since parity work is
    asymmetric (less reads, all encode CPU).

Fix (F144 implements option 2 — random shuffle + online filter):

  - crates/manager/Cargo.toml: new `rand = "0.8"` dependency
    (matches the version already used by autumn-server's CLI).

  - crates/manager/src/lib.rs::select_nodes:
      Replaces both `sort_by_key` calls with
      `pool.shuffle(&mut rand::thread_rng())` then
      `into_iter().take(count)`. The F121 "at least one online
      disk" filter is unchanged; the degraded fallback (no online
      disks observed) is also shuffled instead of returning the
      sorted full set.

  - crates/manager/src/recovery.rs::ec_conversion_dispatch_loop:
      Replaces `HashMap.values().filter().take(extra_needed)` with
      `let mut pool: Vec<_> = ... .filter().cloned().collect();
       pool.shuffle(&mut rand::thread_rng());
       pool.into_iter().take(extra_needed).collect()`.
      Comment explicitly notes the F144 reason so future readers
      don't "optimise" it back to a take-from-iterator.

  - crates/manager/src/rpc_handlers.rs::handle_stream_alloc_extent:
      Replaces `fallback_nodes.sort_by_key(|n| n.node_id)` with
      `fallback_nodes.shuffle(&mut rand::thread_rng())` so per-RPC
      retries don't re-introduce the low-ID bias.

  - crates/manager/src/lib.rs::tests:
      Two new unit tests:
        f144_select_nodes_distribution — runs select_nodes 1000
          times against a 4-node cluster requesting count=3,
          asserts each of the 4 nodes appears in [600, 900] of the
          selections (theoretical mean = 750, std-dev ≈ 14, so
          the bound passes with probability ≈ 1 even without a
          fixed RNG seed).
        f144_select_nodes_degraded_fallback_shuffles — exercises
          the degraded-fallback path (empty disk map) and asserts
          at least 3 distinct first-pick node_ids across 200
          tries.

Out of scope (deferred):
  - Capacity-aware least-allocated selection. Requires a per-node
    `extent_count` (or `used_bytes`) counter persisted in etcd,
    incremented on alloc / decremented on F109 physical delete.
    This is the natural follow-up but is a larger schema change;
    F144 is the minimum-change bias fix.
  - Read-side load balancing (always-replica[0] in failover order).
    Once allocation spreads, the existing read path naturally
    distributes traffic across {1,3,5,7} since different extents
    now live on different replica sets. Read LB is a second-order
    optimisation that should wait for an observed hot-extent
    pattern; raised earlier in the same session and deferred.
