F178 — LevelDB-style sync coalescing — what + why:
  Why:
    F150 Phase B's rotation-trigger barrier put a 5-15 ms (real SSD)
    fsync syscall on the unlucky writer that happened to push past
    FLUSH_MEM_BYTES — typically 1/s under sustained 70 MB/s. p99 spike
    visible in F176 audit (744 ms at 8 MiB; 4 KiB workload less but
    still landed entirely on one writer's path). The writer-side
    barrier was conceptually "wait for log_stream tail durable before
    flush starts"; the right place for that wait is the flush task
    itself (background), not the writer.

  What — Phase 1 (extent_node coalescer):
    - Coalescer struct on each ExtentEntry:
      * last_synced: AtomicU64
      * pending_fsync: AtomicU64
      * inner: RefCell<{ waiters: Vec<(u64, oneshot::Sender)>, task_running: bool }>
    - register_sync_waiter(extent, end_offset) → oneshot::Receiver:
      * push (end, tx) into waiters
      * if !task_running, set true and spawn coalescer_loop
    - coalescer_loop:
      * compio::time::sleep(AUTUMN_EXTENT_FSYNC_COALESCE_MS, default 2)
      * if pending > synced: file.sync_data(); store last_synced=pending;
        wake waiters with end ≤ pending
      * exit if waiters empty AND pending == synced (under inner.borrow_mut
        to close the registration-vs-exit race)
    - handle_append (non-batched) and build_append_future (batched):
      * always advance pending_fsync after pwrite (LevelDB "always
        durable" — the coalescer covers must_sync=false batches too)
      * if must_sync: register_sync_waiter + await receiver
      * On fsync error: all pending waiters fail together (sync_data
        is whole-file)

  What — Phase 2 (drop rotation barrier; flush-time wait):
    - background.rs::start_write_batch: dropped the triggers_rotation
      block. batch_must_sync = batch_must_sync_caller_flag only.
    - extent_rpc.rs: new MSG_SYNCED_LENGTH = 13 (slot recycled from
      retired MSG_SYNC_EXTENT). SyncedLengthReq: 8B [extent_id u64].
      SyncedLengthResp: 9B [code u8][length u64].
    - extent_node.rs::handle_synced_length: returns
      max(coalescer.last_synced, sealed_length). The sealed-length
      bump is load-bearing for old extents the imm spans into —
      apply_extent_meta_durable fsync'd at seal time, so the wait is
      trivially satisfied even before the coalescer has run.
    - client.rs::await_extent_synced_to(extent_id, min_offset):
      * fetch ExtentInfo, resolve replica addrs
      * poll MSG_SYNCED_LENGTH on each replica every
        AUTUMN_STREAM_SYNCED_POLL_MS (default 2 ms)
      * return Ok when ≥ ⌊N/2⌋+1 replicas have synced ≥ min_offset
      * timeout after AUTUMN_STREAM_SYNCED_TIMEOUT_MS (default 30 s)
    - Public alias: await_log_synced_to(extent_id, offset) — same
      semantics, named for the call site.
    - lib.rs::flush_one_imm + flush_one_imm_local: call
      part_sc.await_log_synced_to(snap_vp_eid, snap_vp_off as u64)
      BEFORE row_stream.append. Skip when snap_vp_off == 0 (no
      VPs in the imm yet).
    - F148-A invariant survives: the await sits BEFORE the
      borrow_mut block + save_table_locs_raw mpsc send.

  What — Phase 3 (remove --nosync from clients + perf_check.sh):
