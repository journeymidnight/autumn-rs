F180-B6 — what + why:

  Why:
    F180-B5 (commit 55d254f) lifted per-session ceiling from 44 k → 150 k
    by spawning a compio task per SQE. But aggregate plateaued at ~137 k
    on 16-thread × d=8 because the daemon's single compio runtime
    saturates one core handling all SQE/CQE traffic + all RPC dispatch.
    Pushing past the 200 k validation gate required either multi-core
    daemon or substantial per-call overhead reduction.

  What — multi-runtime daemon:
    `autumn-ioring-daemon --runtimes N` spawns N OS threads, each with
    its own compio runtime, own ClusterClient, and own UnixListener at
    `{socket}.{idx}` (`.0`, `.1`, …). Sessions are pinned to whichever
    runtime accepted them — no cross-thread state. Backward-compat:
    N=1 keeps the legacy single-socket behaviour (same path as before).
    Bench gains a matching `--runtimes N` flag; worker tid picks
    `socket.{tid % N}`.

  What — cached PS client at OPEN:
    Per ring_fd state is now `OpenedFile { key, part_id, ps:
    Rc<RpcClient> }`. At OPEN we do `cluster.head` (existence) +
    `cluster.resolve_key` + `cluster.get_ps_client` once and cache the
    Rc. At READ we skip `ClusterClient::get_range` entirely — build
    `GetReq{ part_id, key, offset:0, length:0 }` inline and call the
    cached PS directly. Saves several RefCell borrows + 2 hashmap
    lookups + the `call_ps_for_key` retry-closure shell per READ.

  Subtle issue (caught + fixed mid-iteration):
    Initial B6 sent `GetReq.length: sqe.length` (= 4096 for the bench),
    expecting PS to return only the requested slice. PS's
    `resolve_value` then took the `offset!=0 || length!=0` branch which
    does `to_vec()` TWICE (raw_value.to_vec() + v[start..end].to_vec()).
    At 100 k+ ops/s the extra 4 K memcpy on the PS path cost ~25 %
    throughput. Fix: send `length: 0` ("whole value", PS hits the
    one-copy fast path), slice in the daemon. PS-side handler is
    unchanged.

  Results (3-replica TCP cluster, 1 partition, hot single key, 16
           bench threads × depth 8 × 4 KB):
    | config     | ops/s   | notes                                    |
    | B5 r=1     | ~104 k  | re-measured baseline (was 137 k pre-F178/cluster state shifts) |
    | B6 r=1     |  113 k  | +9 % from cached PS client + skip ClusterClient.get shell |
    | B6 r=4     |  208 k  | **passes 200 k gate**                    |
    | B6 r=8     |  203 k  | PS process CPU at 100 % — single-partition saturated |

  Above ~200 k the bottleneck is the single-partition handle_get
  CPU on the PS process. Multi-partition workloads will scale
  further (this bench cluster boots with 1 partition by default).
