Pre-existing VP-offset bug (latent since F165 V1 default-on):
  finish_write_batch + flush_gc_batch + recover_partition all
  computed VP.offset = record_offset + 17 + key.len() (V0 layout).
  Post-F165 records on disk are V1 with a 5-byte envelope prefix
  (sentinel + payload_len), so value bytes are at +22 not +17.
  Every value > 4 KiB written via the regular Put path since F165
  has had its VP pointing 5 bytes too early — reads return the
  last 5 bytes of internal_key (inverted-seq, e.g. [ff,ff,ff,ff,fe])
  followed by (value_len - 5) bytes of value. Latent because:
    - production tests use small values (≤ 4 KiB → inline)
    - F129 multipart used the correct V1 calc (1+4+17 = 22)
    - no test verified content of large VP-path values post-V1
  F186 caught it because client-side striperados puts every chunk
  via plain Put with chunk_size = 4 MiB > VALUE_THROTTLE.
  Fix: `+ 17 +` → `+ 22 +` at three sites.

F186 client-side design:
  - StripeMeta (29 bytes): 8B magic + 1B version + 8B total_bytes
    + 4B chunk_count + 4B chunk_size + 4B CRC32C over first 25.
    False-positive rate against random user values ≈ 2^-96.
  - make_chunk_key: \xff\xfeacv1\xff + user_key_len(BE u32) +
    user_key + chunk_index(BE u64). Sorts after all normal user
    keys; length-prefix prevents user-key ambiguity.
  - PutStreamHandle::send writes chunk to chunk_key via plain
    cluster.put. PutStreamHandle::commit writes the meta blob to
    the user key — its presence is the atomic linearisation point.
    abort best-effort deletes already-written chunks.
  - GetStream auto-detects via StripeMeta::try_decode: striped →
    walks chunks; non-striped → yields blob whole.
  - delete_stream cascades; plain delete only removes meta.
  - 6 unit tests (StripeMeta encode/decode + chunk-key disambiguation
    + sort order).
