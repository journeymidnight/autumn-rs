Task scope: F142 — `must_sync=false` foreground writes break WAL→SST
            durability ordering. User repro: `$AC put XXX.mp4` (with
            `--nosync` per the workload's default) succeeded yesterday;
            after `restart-ps` today, `$AC head` returns the size but
            `$AC get` fails with `ec_read_full_and_slice: offset
            459976209 past decoded payload len 308491269`. Forensic
            evidence shows the bad VP was flushed to a row_stream SST
            yesterday at 23:20 — well before today's F141 work — so
            F141 is not implicated. User chose option A from the
            diagnosis ("pre-flush WAL fsync barrier").

Diagnosis (full chain, captured in feature_list.md F142):
  • `--nosync` foreground put → `start_write_batch` calls
    `append_segments(log_stream, ..., must_sync=false)`
  • Extent-node `handle_append` Direct path writes to page cache and
    SKIPS `file.sync_all()`. `extent.len` advances in memory; the
    StreamClient sees `result.end` advance and the partition memtable
    stores a `ValuePointer` referencing page-cache-only bytes.
  • Memtable rotation → P-bulk flushes the SST via
    `row_stream.append(must_sync=true)`; partition writes
    `meta_stream` checkpoint with `must_sync=true`. SST + checkpoint
    are durable. Their VP targets are NOT durable.
  • Page-cache loss event (Mac reboot, OOM eviction, or even some
    extent-node restart paths) drops the unsynced bytes. SST
    persists; VP now points past the actual durable extent length.
  • Manager seals the extent at the post-eviction commit_length,
    EC-converts the shorter payload, and reads of the bad VP surface
    the "offset N past decoded payload len M" error.

Fix (F142 implements option A — single fsync barrier per imm):

  - crates/stream/src/extent_rpc.rs: new wire codec
      MSG_SYNC_EXTENT = 13
      SyncExtentReq  { extent_id: u64, revision: i64 }    (16 bytes)
      SyncExtentResp { code: u8 }                          (1 byte)

  - crates/stream/src/extent_node.rs:
      • dispatch arm for MSG_SYNC_EXTENT in `dispatch()`
      • `handle_sync_extent` — shard-routing check (matches
        commit_length), revision fencing (returns
        CODE_LOCKED_BY_OTHER on stale revision; bumps + persists the
        meta sidecar on a higher revision, matching the existing
        commit_length contract), then `file_ref(&entry.file)
        .sync_all().await`. No payload, no extent.len change.
        Idempotent — repeat calls just trigger another fsync, which
        is a no-op if the file is clean.

  - crates/stream/src/client.rs:
      • New imports: SyncExtentReq, SyncExtentResp, MSG_SYNC_EXTENT.
      • New public method:
          pub async fn sync_stream_tail(&self, stream_id: u64)
              -> Result<()>
        Loads the stream via get_stream_info, picks the tail
        extent. If sealed (sealed_length > 0) returns Ok early —
        sealed tails can't extend; their page cache state is
        whatever the seal captured. Otherwise looks up replica
        addrs (replicates + parity), fans out MSG_SYNC_EXTENT in
        parallel via futures::future::join_all, and requires
        replicates.len() (K) successful syncs to declare the
        barrier complete. M parity-target failures are tolerated,
        matching the post-EC fault model.

  - crates/partition-server/src/lib.rs::flush_one_imm:
      Inserted the barrier BEFORE the FlushReq to P-bulk:
        if let Err(e) = part_sc.sync_stream_tail(log_stream_id).await {
            return Err(anyhow!("flush_one_imm: WAL barrier sync failed: {e}"));
        }
      Coverage matrix:
        • normal flush (memtable rotation under load): yes
        • flush_one_imm_local (P-bulk failed to spawn): yes (it's
          dispatched AFTER the barrier inside flush_one_imm)
        • flush_memtable_locked (split, drain): yes — calls
          flush_one_imm in a loop
        • background_flush_loop: yes — same dispatch
        • shutdown drain: yes — calls flush_one_imm in the drain
          loop
