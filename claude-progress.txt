Bugs closed by F157:

  Bug 1 — Extent .meta sidecar CRC32C
    File: crates/stream/src/extent_node.rs
    Functions: save_meta, parse_meta, META_SIZE/MAGIC constants
    Root cause: pre-F157 the 40-byte sidecar
      [magic[8] | extent_id[8] | sealed_length[8] | eversion[8] | last_revision[8]]
    had no CRC. parse_meta validated only magic + extent_id; the four numeric
    fields were trusted blindly. Bit rot in any field silently changed
    recovered state at restart. The most impactful field is sealed_length:
    a single bit flip turning a sealed extent's length to 0 makes recovery
    treat the extent as open, accept further appends past the original seal
    boundary, and corrupt every replica's view of the extent's tail.
    Fix:
      - Bump on-disk format from V0 (40 bytes) to V1 (44 bytes with CRC32C
        trailer over the first 40 bytes).
      - magic[7] distinguishes versions: V0 = b"EXTMETA\0", V1 = b"EXTMETA\x01".
      - save_meta always writes V1 with crc32c::crc32c(buf[0..40]).
      - parse_meta dispatches:
          V1: verify CRC; mismatch → None + WARN log
          V0: legacy parse, no checksum + WARN log
          unknown magic: None
    Migration: forward-compatible (V0 files keep working, auto-upgrade on next
    save_meta). Rollback breaks because magic mismatches; acceptable for an
    operator-driven rare path.

  Bug 2 — decode_last_table_locations silent newer-record drop
    File: crates/partition-server/src/lib.rs::decode_last_table_locations
    Root cause: meta_stream is a sequence of [len:u32 LE][rkyv_payload] records.
    Pre-F157 the loop scanned forward and `break`d on any decode failure,
    returning the LAST successful decode. After F155 made rkyv decoding strict
    (bytecheck), any bit rot in a record's payload tripped this break-and-fall-
    back path, silently discarding all valid records that came AFTER the
    corrupted one. Failure mode: partition flushes 5 SSTs, bit flip corrupts
    checkpoint #4, recovery returns checkpoint #3 as authoritative, the 5th
    SST becomes orphan on disk, every VP from log_stream pointing into the
    5th SST's extent is unreachable.
    Fix:
      - On decode failure: log WARN with offset + error, advance past the
        corrupted record using its declared msg_len, continue scanning.
      - Legitimate partial-tail-write behaviour preserved (the
        `total > buf.len()` check still breaks at the end).
      - If msg_len is itself corrupt to point into garbage, damage is bounded:
        next record's length-prefix almost certainly fails decode too, gets
        skipped; eventually exit with `last` populated by the last good one.
      - After-loop summary WARN logs total skip count.
