TaskStatus: completed
Task scope: F151 — Python bindings: asyncio-native refactor.
            Replace the blocking surface in `python/src/lib.rs` with
            awaitable methods that bridge the existing compio worker
            thread to the running asyncio loop via
            `loop.call_soon_threadsafe(fut.set_result|set_exception, …)`.

Why:
  The pre-F151 surface ran a compio runtime on a worker thread but
  the Python-facing methods (`put`, `get`, `delete`, `range`,
  `batch_delete`, `close`) were blocking — each one allocated a sync
  `mpsc::channel`, sent the op, and `recv()`-blocked the calling Python
  thread until the worker completed. Under asyncio that pattern stalls
  the event loop for the duration of every RPC, so the binding could
  not be used inside an async server. The user asked for an asyncio-
  native API: compio still drives the IO, asyncio still drives the
  application, the bridge between them is `call_soon_threadsafe` on
  the asyncio.Future the binding hands back.

Architecture:
  - One detached OS thread runs the compio runtime + the
    `ClusterClient`. Unchanged from before.
  - Channel between Python and worker is now
    `futures::channel::mpsc::unbounded` (was `std::sync::mpsc`). The
    worker `await`s the next op via `StreamExt::next` instead of
    busy-polling with `try_recv` + 1 ms sleep — strictly better
    backpressure + zero idle wakes.
  - Each Op variant carries a `PyHandle { loop: Py<PyAny>, fut:
    Py<PyAny> }`. Python-side every method (a) acquires the running
    asyncio loop via `asyncio.get_running_loop()`, (b) creates a
    fresh `loop.create_future()`, (c) sends the op, (d) returns the
    future. The compio worker, on op completion, re-acquires the
    GIL and calls `loop.call_soon_threadsafe(fut.set_result | …
    set_exception, value)` — `call_soon_threadsafe` is the only
    asyncio-blessed cross-thread wake primitive.
  - `Client.connect(addr)` is itself an async classmethod. It
    spawns the worker thread; the worker performs
    `ClusterClient::connect(...).await`, then re-acquires the GIL
    to construct the Python `Client` object (which owns the `tx`
    Sender) on the worker side and resolves the future with it.
    Failure path: `set_exception(RuntimeError("connect failed: …"))`
    and the worker exits.
  - `close()` sends `Op::Close { handle }`; the worker resolves
    the handle, breaks out of the event loop, and the runtime
    drops. The thread is detached (no JoinHandle held) — `Drop`
    on the Python `Client` just drops the Sender, the worker
    observes channel disconnect and tears down. No Python-side
    lifetime hazards because the worker thread holds the GIL only
    for the brief notify call.
