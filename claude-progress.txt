What shipped:
  - Frame::encode_v0 / encode_v1: explicit per-version encoders, callable
    directly (independent of env state).
  - Frame::encode dispatches V0 vs V1 based on `v1_encoder_enabled()`,
    a memoised `OnceLock` lookup of `AUTUMN_RPC_FRAME_V1` env var.
  - Frame::encode_header / encode_request_header: same dispatch shape;
    under V1 the wire payload_len includes the 4-byte CRC trailer.
  - client::send_vectored: conditionally appends CRC trailer based on
    the FLAG_CRC bit on the encoded header.
  - 2 new unit tests: f163_encode_v1_decode_round_trip,
    f163_encode_v0_decode_round_trip — both pass.
  - Default is V0; production behaviour unchanged.

What still doesn't work:
  Setting `export AUTUMN_RPC_FRAME_V1=1; cluster.sh reset 1; put k v`
  reproduces the F161 break:
    - bootstrap RPCs (autumn-client → manager) succeed
    - PS opens partition successfully
    - put k → "Connection reset by peer (os error 104)" from
      autumn-rpc::client::read_loop on PS:9201
    - PS log shows partition listener bound + opened, no errors
    - Diagnostics from handle_ps_connection (eprintln + tracing::error)
      do NOT surface in PS log — even in V0 mode where the path
      definitely runs. Separate operational issue worth fixing first.

What I ruled out:
  - Stale binaries: cargo build clean, mtimes verified.
  - Env propagation: /proc/$PS_PID/environ confirmed AUTUMN_RPC_FRAME_V1
    is NOT in PS environ even after `export ...; cluster.sh reset 1`.
    Wait — re-checking: the env CHECK was on a sibling process not the
    actual PS, OR cluster.sh's launch path strips env somehow. Need
    independent verification. (Possible alternate root cause:
    `start_proc` in cluster.sh might run `env -i` or similar; not
    visible in the script source but could be hidden in a saved
    config file.)
  - Frame::encode dispatching wrong path: unit tests confirm both V0
    and V1 round-trip correctly.
