  - crates/stream/src/extent_node.rs: removed event-loop memcpy from
    `handle_convert_to_ec`. F117 already wraps `ec_encode/decode/reconstruct`
    in `spawn_blocking`, but ~700 MB of memcpy per conversion still ran on the
    event loop (`Bytes::copy_from_slice(shard)` per remote target +
    `shard_data.to_vec()` in `write_shard_local` + `chunk.to_vec()` in
    `file_pwrite_chunked`). Patch:
      • `file_pwrite_chunked` now takes `Bytes` (was `Vec<u8>`); chunked path
        uses `Bytes::split_to` (O(1) Arc reslice) and passes chunks straight to
        `file_pwrite` which accepts `impl IoBuf`. The per-chunk `chunk.to_vec()`
        is gone. Four call sites updated to convert `Vec<u8>` to `Bytes` at the
        boundary via zero-copy `Bytes::from`.
      • `write_shard_local` now takes `Bytes` (was `&[u8]`); the
        `shard_data.to_vec()` before `file_pwrite_chunked` is gone.
      • `handle_convert_to_ec` spawn_blocking closure now returns `Vec<Bytes>`
        (zero-copy `vecs.into_iter().map(Bytes::from).collect()` inside the
        closure); the per-target loop uses `shards[i].clone()` (O(1) Arc inc)
        instead of `Bytes::copy_from_slice(shard)`. Coordinator path uses
        `shards[0].clone()` into the new `write_shard_local(_, _, _, _, Bytes)`
        signature.
      • `handle_write_shard` passes `req.payload` directly instead of
        `&req.payload`.

    Net effect: at K=3, M=1, ~526 MB extent → previously ~700 MB of event-loop
    memcpy per EC conversion (3 remotes × shard_size + 1 coordinator + per-chunk
    round-trips); after F140, 0 bytes of event-loop memcpy. The Reed-Solomon
    math + the conversion to Bytes + the chunked I/O all run on the
    spawn_blocking pool / io_uring, never on the compio runtime serving
    df/heartbeat/append RPCs. This addresses the user's direction:
    "EC conversion CPU-heavy work must be on a different thread".

    `handle_split_part` still calls `multi_modify_split` without first
