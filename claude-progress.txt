Fix discovered during E2E:
  recovery_dispatch_loop's pre-F211 short-circuit (probe ok → no
  dispatch) prevented fence-triggered recovery on a Fenced node
  whose probe still succeeded (the node was operator-marked dead
  but the underlying process was still running). Added an explicit
  "if is_fenced → dispatch immediately, skip probe shortcuts" arm
  in recovery_dispatch_loop. Crystallised by the
  fence_triggers_recovery_dispatch e2e test which hung for 60 s
  pre-fix; passes in ~5 s post-fix.

Behaviour notes:
  - Default AUTUMN_MGR_RECOVERY_GATE = fenced_only (BACKWARD-INCOMPAT)
    Operators who haven't deployed the F211-G policy script can flip
    to AUTUMN_MGR_RECOVERY_GATE = auto_disk to restore pre-F211
    behaviour while they roll out the script.
  - Recovery limiter defaults: per_source=4, per_target=2, global=64
    (env: AUTUMN_MGR_RECOVERY_MAX_{PER_SOURCE,PER_TARGET,GLOBAL})
  - Backoff: 2^N seconds capped at 300 s per (extent, slot) failure
  - NodeStateTracker soft timeout: 10 s
    (env: AUTUMN_MGR_NODE_SUSPECTED_TIMEOUT_SECS)
  - Audit retention: 90 days
    (env: AUTUMN_MGR_AUDIT_RETENTION_DAYS)
  - F211-D shard fence: ALL existing call sites pass revision=0 (no
    fence). Future work: thread the manager's per-extent revision
    through ExtConvertToEcReq so the WriteShard/CommitEcShard fanout
    inside handle_convert_to_ec carries the live revision and a
    fenced ex-coord is rejected at the shard handler too. The wire
    + handler scaffolding is in place; only the caller-side
    propagation remains.
