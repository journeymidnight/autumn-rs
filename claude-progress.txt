TaskStatus: completed
Task scope: F153 — Close post-failover double EC dispatch race via per-extent
            serialisation lock on the coordinator (defense-in-depth approach).
            ~30 LOC core change + invariant comments + 1 unit test.
            Ships the second item from F152's deferred candidate list.

Why:
  The F152-era multi-round audit verified that the manager's
  `ec_conversion_inflight` set is purely in-memory and is lost on leader
  failover. A deposed leader's mid-`spawn_blocking ec_encode` +
  `write_shard_local` call (per CLAUDE.md note 15, 100-300 ms encode +
  shard fanout RTTs — easily multi-second) is invisible to the new
  leader. The new leader's 5 s `ec_conversion_dispatch_loop` re-fires a
  duplicate `EXT_MSG_CONVERT_TO_EC` for the same extent.

  F119-D's coordinator-side idempotency guard fires post-hoc — the
  eversion bump is the LAST step of the 2PC (`commit_shard_local` ->
  rename + save_meta + entry.eversion.store), so during the window
  between dispatch-1's start and dispatch-1's commit, dispatch-2 sees
  `entry.eversion < req.eversion` and proceeds. Two concurrent encodes
  race on the same `.ec.dat` staging file, producing the F119-D
  corruption shape: `logStream value short: need N got M` on cross-shard
  VP reads, or `ec_read_full_and_slice: offset N past decoded payload`
  on SST recovery during partition open.

How (defense-in-depth, not root-cause):
  Per-extent `Rc<futures::lock::Mutex<()>>` map on `ExtentNode`,
  acquired at the very start of `handle_convert_to_ec` (before any
  state inspection), held across the entire prepare + commit phase.
  The second concurrent dispatch awaits the first; when the first
  releases, the second re-runs the F119-D guard UNDER the lock — at
  which point `entry.eversion` IS bumped (the first dispatch's
  `commit_shard_local` ran while the second was waiting), so the
  second exits as a no-op. Pattern mirrors `client.rs::stream_init_locks`.

Architectural choice — why defense alone, not root cause:
  The full root-cause fix would persist `ecConversionInFlight/$extent_id`
  to etcd with a create_revision==0 CAS, mirroring the F149
  `recoveryTasks/$id` pattern. ~150 LOC: new etcd key prefix, dispatch
  loop CAS, replay rebuild, lease attachment for orphan reaping.
  Defense alone (this F153) is sufficient for CORRECTNESS: the F119-D
  guard becomes load-bearing AFTER the lock, so the worst observable
  behaviour is a wasted RPC round-trip (network + the second
  dispatch's `entry_info_from_manager` fetch) instead of corrupted
  shards. Root-cause fix becomes optional perf hygiene; left as F154
  candidate.

Memory footprint:
  `HashMap<u64, Rc<Mutex>>` grows monotonically with extents ever
  EC-converted on this shard. ~64 bytes per entry. 10 k extent
  cluster → ~640 KB per node, same order as the existing `extents`
  DashMap; not worth GC'ing.
