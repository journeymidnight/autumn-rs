TaskStatus: completed
Task scope: F206 — post-EC `avali` not refreshed, causing infinite
            RE_AVALI loop with multi-GB RSS churn on restart.

User-driven diagnosis (turn-by-turn):
  - User question 1: "sh cluster.sh restart 4 后 macOS 上的
    extent node 为什么占用这么多内存？"
  - First investigation pass: confirmed processes alive, all 4
    nodes hold the same 941 MB extent-10.dat (3+1 EC shard size,
    matches sealed_length / K = 2961566856 / 3), RSS rotates
    among nodes (2 MB / 2.6 GB / 596 MB / 1.84 GB then
    decreasing/redistributing). `vmmap` confirmed MALLOC_LARGE
    (empty) 2.8 GB / 24 regions / peak footprint 4.6 GB — large
    allocations freed but held by allocator's free list.
  - User pushback 2: "EC 跑完了但 manager 仍然不知道，这是
    严重的 BUG！" — diagnosis correction: manager DOES know
    (`/streams --json` shows `ec_converted: true, eversion: 4,
    parity: [7], replicates: [3, 5, 1]`), BUT the avali bitmap
    was never refreshed post-EC.
  - Found exact bug pair: Bug A in
    `crates/manager/src/recovery.rs::apply_ec_conversion_done`
    (misses `avali` update), Bug B in
    `crates/stream/src/extent_node.rs::handle_re_avali` (compares
    local shard size to logical sealed_length without checking
    `ec_converted`). The two bugs combined to drive the
    recovery loop into firing RE_AVALI on the parity holder every
    2 s, which triggered fetch_full_extent_from_sources to
    allocate ~941 MB per peer attempt (4 peers × 941 MB ≈ 3.7 GB
    per tick).
  - User said "ok" to proceed with the surgical fix.

What was changed:

  1. `crates/manager/src/recovery.rs` — added one line in
     `apply_ec_conversion_done`:
         ex.avali = Self::all_bits(target_nodes.len());
     plus a multi-paragraph comment block explaining the
     RE_AVALI / fetch_full_extent_from_sources chain that the
     missing assignment had enabled.

  2. `crates/stream/src/extent_node.rs::handle_re_avali` —
     short-circuit `CODE_OK` return when
     `extent_info.ec_converted == true`, placed AFTER
     `apply_extent_meta_durable` (so local meta still refreshes
     from manager on stale eversion) but BEFORE the
     `local_len >= sealed_length` check. Also load-bearing as
     the self-heal migration path for pre-F206 etcd entries.

  3. `crates/manager/src/lib.rs` — new unit test
     `f206_apply_ec_conversion_done_sets_avali_for_all_shards`.
     Pre-EC fixture has K=3 replicas + avali=0x7; calls
     apply_ec_conversion_done with target_nodes=[1,3,5,7]
     (K=3+M=1); asserts ex.avali == 0xF post-call.

  4. `crates/manager/tests/system_extent_recovery.rs` — tightened
     existing assertion from `ext.avali > 0` to
     `ext.avali == all_bits(replicates + parity)`. The old
     looseness is exactly what let F206 ship undetected.
