【为什么这段可以删】
  它不是作用域段。tenant/agent 承担隔离与授权（grant 打在 `mem/{tenant}/` 上），
  而 `{namespace}` 唯一的作用是给 `list_facts` 当扫描前缀。`q()` 是无状态逐字节
  循环 ⇒ `q(a ++ b) == q(a) ++ q(b)`，**编码保前缀**；且它的 token 集合
  （{单个 unreserved 字符} ∪ {`%XX`}）**前缀无关**（`%` 绝不作单字符 token 出现），
  所以前缀匹配落不到 token 中间。分组因此可以写进 key 本身，
  `list_facts(Some("profile:"), …)` 扫 `fact/` ++ `q(组)` 与专设一段等价。
  注意**依据是前缀无关，不是「定宽」**——token 是 1 或 3 个字符。我第一版三处
  都写成了「定宽 token」，评审纠正。

【换掉的两件事（已写进文档，不要再当成"纯赚"）】
  ① 分隔符归调用方：`fact/{ns}/` 的尾随 `/` 免费保证 `profile` 看不见 `profiles`，
     扁平 key 没有 ⇒ 组串必须自带终止符（`Some("profile:")`）。
  ② `(ns, key)` 原本单射，扁平 key 不是：`("a","b/c")` 与 `("a/b","c")` 曾是两个 key。

【评审抓到的实质缺陷：老 key 在范围内，不是"看不见"】
  我在 ops.md 写过「旧 `fact/{ns}/{key}` 落在不同字节区间、新读路径看不见」——**反了**。
  `fact/profile/name` 排在新族范围**里面**，会被列出来，名字读回是 `"profile/name"`，
  再编码成 `fact/profile%2Fname` —— 另一个 key。于是 `get_fact` 查不到、
  `delete_fact` 删不掉任何东西**且报成功**。这正是本仓库反复吃亏的「失败伪装成成功」。
  修法：`keys::fact_key_is_canonical` + `list_facts` 见到非规范 key 整次扫描以
  `PreconditionFailed` 报出该 key（fail-loud；crate 无 tracing 依赖，静默跳过等于
  换一种方式撒谎）。这个洞旧 schema 其实也有，本次改动把它扩大到全族扫描。

【2026-09-04 BUG-EC-CONVERT-STALL 定谳：toxiproxy 修复"上报成功但没生效"】
  **结论：产品没坏，harness 坏了。** 而且坏的方式正是我一直在别处防的那一类——静默的默认值。
  `ToxiproxyCli::is_enabled` 解析 `toxiproxy-cli inspect` 找 `Enabled:` 行，找不到就

  `set_enabled(x,false)` 能工作（true≠false → toggle），`set_enabled(x,true)` **静默空操作**。
  **不是"每次 partition 都变永久"（我第一版这么写，错了，fable 纠正）**：受害节点是
  `.find()` 确定性选的、且 `partitioned` 每次都被清空，所以**同一节点的第二次 partition
  会把已 disabled 的代理 toggle 回 enabled** —— 治好了上一刀、这一刀什么也没注入。
  节点的可达性 = 命中它的 partition 事件的**奇偶性**。这才解释得了为什么是 ~50% flake 而不是必挂。
