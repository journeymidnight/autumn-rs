Task scope: F198 — fix EC dispatch stuck-state on restart (rich
            `ecConversionInflight/` marker + replay-aware dispatch +
            PS open eversion-mismatch retry).

User-reported bug (2026-05-14):
  - `sh cluster.sh reset 4`, write large values to partition 15, split
    15 + compact 15 several rounds, macOS slows down, then
    `sh cluster.sh restart 4`.
  - PS startup fails on partition 15 with `read SST from rowStream
    extent=20 offset=0: eversion mismatch (stale extent_info_cache)`.
  - `partition 15 thread exited before reporting listener readiness`.

Root cause:
  1. EC conversion was mid-flight when the cluster died. The
     extent-node's `commit_shard_local` bumped local eversion + wrote
     shard data, but the manager's `apply_ec_conversion_done` didn't
     commit to etcd. Etcd still has the pre-EC eversion.
  2. On restart, the manager replays the etcd marker (F173) — but
     the marker was empty. The dispatch loop body had
     `if ec_conversion_inflight.contains(&id) { continue; }` which
     permanently SKIPPED replay-loaded markers. Etcd state never
     converged.
  3. PS reads pulled `ExtentInfo.eversion` from manager (stale,
     pre-EC) and sent it in `ReadBytesReq`. Extent-node's
     `req.eversion < ev` check rejected with CODE_EVERSION_MISMATCH.
     PS's 2-attempt `read_bytes_from_extent` refetch loop got the
     same stale eversion every time → recover_partition failed →
     partition thread exited.

Why F119-D + F173 alone didn't cover this:
  - F119-D coordinator idempotency is fine for re-dispatch.
  - F173 persisted the lock-set but used an EMPTY marker value.
    Replay-loaded markers couldn't be safely re-dispatched without
    the original `target_nodes` (a fresh `shuffle().take(extra)`
    + `alloc_extent_on_node` would reset an already-converted
    parity node's in-memory state and overwrite its .meta sidecar
    — silently corrupting the EC layout. Manager would then commit
    `ex.parity = [random_node]` to etcd, pointing AWAY from the
    node that actually holds the parity shard).

Fix (F198):
  - New rkyv struct `MgrEcDispatchInflight { extent_id,
    target_nodes, extra_disk_ids, data_shards, new_eversion }` in
    `crates/rpc/src/manager_rpc.rs`.
  - `persist_ec_conversion_inflight(&record)` (signature changed) now
    serialises the record into the etcd marker value.
  - `replay_from_etcd` decodes marker values into
    `pending_ec_dispatch: Rc<RefCell<HashMap<u64,
    MgrEcDispatchInflight>>>`.
  - `ec_conversion_dispatch_loop` body checks
    `pending_ec_dispatch.get(&extent_id)` first. On replay match:
    reuse persisted target_nodes + extra_disk_ids + new_eversion
    exactly (no shuffle, no `alloc_extent_on_node`).
  - Old `if ec_conversion_inflight.contains(&extent_id) { continue; }`
    gated on `replay_params.is_none()` so concurrent-dispatch
    semantics within a single process are preserved.
  - Initial dispatch delay reduced from 5 s → 500 ms (one-shot)
    so post-restart convergence is fast.
  - PS-side `recover_partition` SST read wraps
    `read_bytes_from_extent` in a 30 × 1 s retry on
    `eversion mismatch` so the user's first `cluster.sh restart`
    succeeds without a second manual restart — manager converges
    within ~1 tick.
