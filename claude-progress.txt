Root cause of F161 + F163 "break":
  cluster.sh:16 sets BIN="$SCRIPT_DIR/target/release" and launches all
  server processes from target/release/. My F151-F163 work was being
  compiled into target/debug/ via `cargo build --workspace`. The
  RELEASE binaries on disk were from May 7 06:09 — 24 hours old,
  predating F155's rkyv checked-decode bytecheck.

  When I set AUTUMN_RPC_FRAME_V1=1 and tested, the autumn-client (run
  from ./target/debug/autumn-client) sent V1 frames with 4-byte CRC
  trailer. The cluster's release PS / manager / extent-node binaries
  used pre-F155 from_bytes_unchecked rkyv decoder which silently
  mis-read the trailing CRC bytes as part of the rkyv archive.
  PutReq's part_id field decoded to garbage (e.g. 18446744004990074880,
  close to u64::MAX), extract_part_id returned that, leading to
  "partition NOT_FOUND part_id=garbage" errors.

  Diagnostics from handle_ps_connection (eprintln/tracing) never
  showed up because the running PS binary was the OLD release one
  without my added prints. F164 startup env-dump also never showed
  up for the same reason.

Lesson learned (process):
  When a code change appears to break an integration test, FIRST
  verify the binaries-under-test are actually the ones containing
  the change. `cargo build --workspace` builds DEBUG; `cluster.sh`
  runs RELEASE. Two iterations of F161+F163 burned trying to debug
  a "cluster break" that was just a stale-binary mismatch.

  Future iterations should add a quick `target/release/autumn-ps`
  mtime check before assuming "my code change is broken". Or
  cluster.sh could be modified to use debug binaries in dev mode
  (out of scope this iteration).
