=== THE BUG (confirmed by code + now by test) ===
  F178 per-extent fsync coalescer credits an ACK to bytes written AFTER the
  covering fsync, under OUT-OF-ORDER same-extent append completion.
  - build_append_future / handle_append do `pending_fsync.store(total_end)` —
    a PLAIN store, AFTER the pwrite .await (extent_node.rs ~1824 / ~4350).
  - extent.len is reserved synchronously at build (step 7 ~1789) so two
    same-extent futures in the inflight FU get ascending non-overlapping
    file_starts — BUT their pwrite CQEs can complete out of order.
  - RACE: F1=[0,100) F2=[100,150). F2 completes first → store(150) → coalescer
    fsync → last_synced=150 → F2 ACKs. F1 completes LATE → store(100)
    (REGRESSES pending, plain store not fetch_max) → register waiter(100) →
    coalescer `pending(100) <= synced(150)` branch (~624) satisfies it WITH NO
    FRESH FSYNC → F1 ACKs. But [0,100) was written AFTER the only fsync.
  - fetch_max ALONE does NOT fix it: even keeping pending=150, last_synced=150
    was set by a fsync that ran before [0,100) was written. Correct fix =
    CONTIGUOUS COMPLETED-PREFIX tracking (last_synced may only advance over a
    fully-written prefix). NOT applied (hot-path, revert-prone).

=== REPRODUCTION (committed, test-only) ===
  crates/stream/src/extent_node.rs new `#[cfg(test)] mod p0_fsync_highwater_tests`
  (had to be IN-CRATE — Coalescer / register_sync_waiter are pub(crate), the
  out-of-crate tests/ dir can't see them):
  - p0_coalescer_acks_write_that_completed_after_fsync: drives the high-then-low
    completion order on a real tmpfile ExtentEntry, asserts waiter(100) resolves
    Ok WITH last_synced UNCHANGED at 150 → proves the no-fsync ACK (the bug).
  - p0_in_order_completion_is_correctly_durable: control — in-order completion

  Both pass. autumn-stream lib 65→67 tests; clippy clean.

=== REACHABILITY / SEVERITY (why it's a repro, not an incident) ===
  - Needs 2+ concurrent SAME-extent append futures: the hot path COALESCES
    consecutive same-extent frames in one read burst into ONE pwritev; two
    futures only coexist when same-extent appends straddle read-burst
    boundaries → MINORITY case. Plus io_uring must complete them out of order.
  - ACK-before-fsync loss is observable ONLY under POWER LOSS / kernel panic /
    block-layer flush-fault injection. A PROCESS KILL does NOT drop un-fsynced
    page-cache writes (kernel writes them back after the process dies) → NO
    process-kill chaos can EVER surface this. Same harness-invisible class as
    the deferred extent-state CAS. This is why it has never been observed.
  - F227 all-replica-ACK + recovery: a user PUT ACKs only when ALL 3 replicas
    ACK; single-replica power loss in the µs window re-replicates from the 2
    healthy peers. User-visible loss needs the race + correlated multi-replica
    power loss in the same µs window → structurally near-precluded.

MULTI-PS STATUS (answer to the user's question)
=========================================================================
1. MULTI-PS REGISTRATION/DISCOVERY — SUPPORTED.
   - Manager keeps a PS registry: MetadataState.ps_nodes: HashMap<ps_id, addr>
     (crates/manager/src/rpc_handlers.rs), heartbeat liveness in
     ps_last_heartbeat. RPCs: register-PS, heartbeat-PS (unknown ps_id →
     CODE_NOT_FOUND → PS self-evicts). PS liveness loop evicts a PS that
     misses its heartbeat window, then rebalances.

2. PARTITION FAILOVER (PS dies → another PS opens the partition) — SUPPORTED.
   - Each partition has exactly ONE owner PS: MgrRegionInfo.ps_id.
   - On PS eviction, rebalance_regions() reassigns its partitions to the
     remaining least-loaded PS and persists to etcd.
   - PS polls the manager (sync_regions_once, ~2s); when a region's ps_id ==
     self it open_partition()s (replays log_stream from the VP checkpoint),
     and drops partitions no longer assigned to it.
   - Split-brain prevented by owner-lock revision fencing: the new owner
     acquires a higher revision; the old owner's appends/commits are refused
     (durable owner_revision fence, Item 1 / db5d708).
   - Covered by crates/manager/tests/system_ps_failover.rs (PS1 dies → keys
     reassigned + recovered on PS2).

3. CROSS-PS PARTITION MIGRATION (proactive move for load balance) —
   NOT SUPPORTED (by design). No migrate/move/transfer RPC exists.
   rebalance_regions() is REACTIVE only (fires on register / upsert / split /
   PS eviction) and PRESERVES existing assignments while the owner is healthy.
   Load rebalancing today is indirect: operator-driven split (relief valve) /
   merge shifts partition boundaries; the manager is mechanism, policy is
   external (F183/F185, see project_auto_split_before_merge memory).
   → A graceful "drain partition A from PS X to PS Y without killing X" path
     does not exist. If wanted, it is a NEW feature (proactive-migrate RPC:
     freeze-source → seal/handoff owner-lock → open-on-target → reroute
     clients). Relevant caution: the drain-before-reopen attempt in the
     reopen-overlap work DEADLOCKED on client port migration (see history),
     so a migration design must solve old↔new handoff carefully.
