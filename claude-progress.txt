【2026-09-04 BUG-EC-CONVERT-STALL 定谳：toxiproxy 修复"上报成功但没生效"】
  **结论：产品没坏，harness 坏了。** 而且坏的方式正是我一直在别处防的那一类——静默的默认值。
  `ToxiproxyCli::is_enabled` 解析 `toxiproxy-cli inspect` 找 `Enabled:` 行，找不到就
  `Ok(true)` 兜底。实测（我在本机起了一个 toxiproxy 亲自复现）：**2.12.0 的 inspect 在管道里
  什么都不打印**（stdout 空、stderr 空、exit 0），带 toxic 时也只打 toxic 行、依然没有状态行。
  所以 `is_enabled` **在任何状态下都返回 true**。后果不对称：
  `set_enabled(x,false)` 能工作（true≠false → toggle），`set_enabled(x,true)` **静默空操作**。
  **不是"每次 partition 都变永久"（我第一版这么写，错了，fable 纠正）**：受害节点是
  `.find()` 确定性选的、且 `partitioned` 每次都被清空，所以**同一节点的第二次 partition
  会把已 disabled 的代理 toggle 回 enabled** —— 治好了上一刀、这一刀什么也没注入。
  节点的可达性 = 命中它的 partition 事件的**奇偶性**。这才解释得了为什么是 ~50% flake 而不是必挂。

  **证据链（都是量出来的，不是推的）**：① marker 现在带
  `attempts=9 last_error="WriteShard to 127.0.0.1:29771 ... Connection refused"`；

  ④ nemesis 事件打时间戳：01:54:48.80 disable（与端口消失同秒）、01:54:51.89 报告 "OK"；
  ⑤ CLI 层直接复现 inspect 空输出。
  **修复**：`is_enabled` 改成解析 `list`（管道下是 tab 分隔：name/listen/upstream/enabled|disabled/toxics），
  解析不了就**报错，绝不兜底**；`set_enabled` toggle 后回读确认。
  **数据**：修复前 4 挂/9 轮；修复后 **13/13 全绿**（含评审修改后再跑的 5 轮，proxy 故障计数 0）；
  消融（把 `is_enabled` 强行改回恒 true）4 轮挂 1。纯函数 `parse_list_state` 有 3 条单测，消融红。

  **fable 评审又救了三处**（都已修）：① 失败注入报错只进一个**从没被断言过**的计数器 ⇒
  以后 CLI 换版本会导致每次 partition 都失败、而整套测试照样绿、那个维度悄悄没了覆盖
  ⇒ 加 `proxy_faults` 并在 verify 里断言为 0；② disable 成功但确认失败时会 `?` 提前返回，

  且受害者已被移出 `partitioned` ⇒ 收尾修复不会重试它，而 ctl 面黑掉会堵住 df（唯一排空
  recovery 完成报告的通道），改成两个面都好了才出账。顺手把 `do_latency_spike` 里
  `let _ = remove_toxic` 也改成报错（同一类：摘不掉的 toxic = 永久 500ms，且不可见）。

  **对历史结论的影响（重要）**：这个 harness bug 在场时，NetworkPartition 之后
  `ctx.partitioned` 被清空 ⇒ `healthy_count()` 把不可达节点算成健康 ⇒ nemesis 预算门

  "修复前 3/8 vs 加修复后 4/8"的单变量隔离——两臂量的都是奇偶噪声，*结论*（stall 早于该 commit）

【2026-09-03 fuse 读 I/O 线程池：已实现并验收】
  形状：N 个独立单线程 compio runtime，各自 `ClusterClient`，`futures::mpsc` 喂 `ReadJob`。
  能这么切是因为 `prepare`/`execute` 早就分好了 —— `prepare` 那一半才要 `&mut FsState`，
  仍然独占派发线程；`execute` 只拿 (key, 子区间, dest 偏移) 的计划。`ReadJob` 天然 Send
  （`fuser::ReplyData` 因 `ReplySender: Send + Sync` 而 Send），client 不跨线程。
  round-robin 派发（和 ino 哈希实测无可分辨差别，取不牺牲"多线程读同一大文件"的那个）；
  派发不出去就把 job 原样还回来在本地跑。`--read-io-threads 0` = 回退到旧行为。
  结果（8 个独立 1 GiB 文件，核对字节数，两轮同向）：p=8 2211 → 3705(t=2) → 4763~5396(t=4)，
  t=4 达 CLI 5466 的 95%~99%。机制验过：p=8 的 per-thread jiffies 派发线程 435 → 7，
  总量 435/427/412 几乎守恒 —— 同一份活摊开到多核。
  验证：`cargo test -p autumn-fuse --lib` 54 绿（含 4 条 submit 路由单测）、core feature 单独
  可编、workspace release 绿、`fuse_chaos.sh` 三次 PASS（77/78/78 文件；末次跑在默认的 4 线程上，日志确认 `threads=4`）。
  fable 评审：无高危；采纳 4 条 —— ①"丢 job = 内核永久挂"是**夸大**（fuser 0.15.1 的
  `ReplyRaw::Drop` 会答 EIO），注释已改准 ②`ready_rx.await` 无上限而 session 已挂载 ⇒
  连不上的 worker 会卡住整个挂载点的系统调用，加 `READY_TIMEOUT` 20s ③threads=0 还打
  "pool ready" 日志 ④clippy `manual_ok_err`。
  **未覆盖**：UCX。默认二进制不带 ucx feature，本机只有 lo 有 IPv4（无 RoCE IP）、跨机不可用。
  UCX worker 创建走宿主级 devx 自旋锁 + fuse 在 UCX 上崩过 daemon ⇒ 真跑 UCX mount 要先拿
  `--read-io-threads 0` 对照。
  默认取 4（用户定）：p=8 3705 → 4763~5396。代价里最大的一项不是连接而是**每线程的注册
  缓冲池**（`REGPOOL_CAP_BYTES` per-thread 512 MiB，规则 `cap × threads < RLIMIT_MEMLOCK`），
  容器侧补了 `AUTUMN_FUSE_READ_IO_THREADS` env→flag 翻译，受限 pod 能不换镜像调回 0。
  **F-FUSE-READ-GAP 仍 `passes: false`**：验收线写的是"单流进到 CLI 的 80%"，而单流是每请求
  延迟绑定的（内核对同步读者不并发下发；bdi read_ahead_kb 128→32768 实测完全无效），
  线程池按定义改不了。聚合吞吐已追平 CLI。按规则不改写验收口径，只记状态。

【2026-09-03 BUG-EMPTY-VP-CURSOR-PUNCH：复现 → 修复 → 消融，静默丢失已 ACK 写入】
  这是本会话最重的一条，而且**不是本轮引入的**，是 shipped 代码里的潜伏类。
  链条：恢复把写游标种成 committed tail，而刚 roll 出来的尾巴零字节 ⇒ 游标 = `(E, 0)`；
  下一次 rotate 把它盖进 SST 和 meta checkpoint；E 离开尾巴位后就是 sealed-empty，
  而 `gc_extent_punchable` 是 `sealed_length == 0 || pos < floor` —— **空的一律可回收，
  重放下限保护不了它**；游标解析不到就跳过，若全部解析不到而 tables 非空 ⇒ `chosen_pos == MAX`
  ⇒ 旧代码**一条 WAL 都不重放**。compaction 把输出 SST 统一盖成流位置最大的 vp_head，
  所以"全都解析不到"是常态而非corner。
  **复现**（`crates/manager/tests/system_empty_vp_cursor.rs`，真集群真重启）：修复前 `a-*`（已进 SST）
  幸存、`c-*`（**已 ACK** 未 flush）**全部消失**，分区干净打开、无任何告警。
  **修复**：`chosen_pos == usize::MAX && tables.is_empty()` → `chosen_pos == usize::MAX`。
  红 → 绿 → 消融重新变红；215 单测 + 8 个恢复/重放系统测试全绿。
  **fable 抓到我注释里一条 materially false 的话**（已核实并改）：我写"按来源区间去重"，
  但那条路**不会执行** —— `records_meta` 每项都要 `first_pos_by_eid` 命中，而"全都不命中"正是
  `chosen_pos == MAX` 的成因 ⇒ 必然走全局并集那条 legacy 路径。过度重放依然安全
  （ts > 全局 max ≥ 任何已 flush 的 seq），但机制不是我写的那个；另有一个**欠重放**的窄 corner
  （post-merge 多来源时可能跳过 ts ≤ victim max 的 survivor 记录），严格优于"全丢",已记在注释里。
  另外补了：全量重放分支的 WARN（它会读整条日志，必须自报）、4 处仍把"不重放分支"当现状的陈旧注释。
  **一条建议我没采纳并写明理由**：改用 `start_partition_server_stoppable` 会走优雅 drain 从而 flush，
  把测试依赖的"未 flush 的 C"冲掉 ⇒ 测试会**假绿**。
  **一处保真度缺口如实标注**：生产回收者是 PS 的 GC，但本 harness 里 AUTO_GC 什么都没收

  且第二次 roll 之前 E 还是尾巴、本就被排除）。测试改用与 `run_gc` 空路径**逐字节相同**的
  `MSG_STREAM_PUNCH_HOLES`，所以钉住的是"回收游标 extent 的后果"，不是"GC 就是回收者"。
