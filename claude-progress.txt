Headline:
  After F207-C, ALL stream-layer ops in flight on any extent live in
  ONE etcd-backed source of truth (`extent_inflight/<id>` prefix +
  `AutumnManager.inflight` in-memory map). The four scattered
  pre-F207 inflight bookkeeping mechanisms (ec_conversion_inflight
  HashSet, pending_ec_dispatch HashMap, recovery_tasks HashMap,
  pending_extent_deletes VecDeque) are gone. The five F-numbers
  (F126/F138/F139/F145/F147-A) that each implemented "if-extent-in-set
  then refuse" across nine sites all consult the same probe now.

Writer migration:
  - dispatch_recovery_task (recovery.rs:13-…): three-way refuse-at-start
    (recovery_tasks dedup + ConvertToEc check + pending_extent_deletes)
    collapsed to one extent_inflight_op probe; etcd CAS + in-memory
    insert pair replaced with one acquire_extent_inflight(eid,
    Recovery(task)) call.
  - apply_recovery_done (recovery.rs:144-…): atomic three-key
    put_and_delete txn (extents/<id> + extent_inflight/<id> + legacy
    recoveryTasks/<id>) under F149 fence. Pre-F207-C race window
    between etcd write and in-memory recovery_tasks remove is closed
    structurally. Orphan-cleanup path now releases Recovery before
    acquiring Delete (ledger-exclusive-per-extent semantics).
  - recovery_collect_loop (recovery.rs:408-…): tasks sourced from
    inflight filter Recovery-kind; same df-grouping + apply fan-in.
  - enqueue_pending_deletes (extent_delete.rs): now async — each
    enqueue acquires a Delete entry in the unified ledger (etcd CAS +
    F149 fence). Successful acquires populate the in-memory
    delete_progress: HashMap<u64, PendingDelete> map.
  - extent_delete_loop (extent_delete.rs): drains delete_progress
    (was pending_extent_deletes VecDeque). Per-attempt live state
    stays in-memory only; attempts reset to 0 on leader failover
    (correct semantics — a new leader's first attempt is its own
    "attempt 1"). On full-ack or max-retries-exhausted, calls a new
    private release_delete_marker helper.
