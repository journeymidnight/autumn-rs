Root-cause recap (from the user-reported symptom):
  - User restarted cluster with pre-F207 binary at some point,
    which left `recoveryTasks/{21,23}` etcd markers behind.
  - User upgraded binary to F207-C.
  - F207-C's `replay_from_etcd` "one-cycle backward compat" code
    folded those legacy markers into the unified ledger as
    `ExtentOpPayload::Recovery` records.
  - In-memory ledger now had Recovery in flight on extents 21
    and 23, but no EN was actually running those tasks (they
    were orphans from a dead prior manager).
  - PS's `alloc_new_extent` saw Recovery in flight on the tail
    extent (23) and refused with Precondition.
  - PS retried 20 times every 500ms, gave up — write path
    blocked forever.
  - Recovery_collect_loop's df probe found no `recovery_done`
    entries (because the EN tasks were never started under the
    new manager's lifetime), so the ledger entries never cleared.
  - Permanently stuck.

F207-D mitigation (already shipped at commit 18adeeb): removed
the fold-in. Kept a WARN-on-detect scan so an operator would see
orphan etcd state and run a Python ops scrub script.

F207-E (this commit): user said no need for backward compat.
Future deploys go through `cluster.sh reset` (which clears etcd)
when crossing the F207 boundary. Drop the WARN scan entirely.

What F207-E removes:
  - `let legacy_ec_inflight = c.get_prefix("ecConversionInflight/")`
    query in `replay_from_etcd`.
  - `let legacy_recovery_tasks = c.get_prefix("recoveryTasks/")`
    query in `replay_from_etcd`.
  - The two WARN-emission blocks that fired on non-empty results.
  - A comment block in `replay_from_etcd` referencing the scrub
    workflow.

What F207-E DOES NOT change:
  - `extent_inflight_stale_sweep_loop` (24-hour stale-marker
    WARN) — still in place. That's for NEW stale markers
    (acquired but never released), a different scenario from
    pre-F207 legacy orphans.
  - `apply_ec_conversion_done` / `apply_recovery_done` delete
    batches — already F207-D-clean (only touch new ledger key).
  - F207 unit tests — none referenced the legacy scan.

Why this is safe (the EN-side independence argument):
  - EN's `handle_require_recovery` (crates/stream/src/extent_node.rs:3422)
    detaches `run_recovery_task` via `compio::runtime::spawn`,
    returns CODE_OK to manager immediately, and pushes
    completion to `recovery_done` for the next manager df probe
    to drain.
  - EN's `handle_convert_to_ec` has F119-D + F153 idempotency
    guards (eversion-based no-op if already converted).
  - Manager-side markers are "commands-already-sent receipts",
    not authoritative work tracking.
  - A new leader either (a) sees the EN report completion in df,
    or (b) re-dispatches via the recovery/EC convert loops and
    EN-side idempotency makes the re-dispatch a no-op.
  - No legacy etcd state is load-bearing.

Migration policy going forward:
  - F207 is a ONE-WAY etcd schema migration.
  - Pre-F207 → F207 requires `cluster.sh reset` (full data +
    etcd wipe).
  - The operator-facing contract is documented in
    crates/manager/CLAUDE.md programming note 21 (updated by
    this commit with a "No backward compatibility with pre-F207
    etcd state" paragraph).
