TaskStatus: completed
Task scope: F158 — WAL record per-record CRC32C (V1 envelope). Closes the
            last verified on-disk silent-corruption surface from the
            data-corruption audit (Audit 1 #3). Also formally clears
            Audit 1 #4 (VP offset bit-rot) after verifying SST block CRC
            covers stored VP entries.

Why:
  Pre-F158 each log_stream record was 17-byte header + variable payload
  with no CRC. A bit flip in the header silently mis-parsed the record:
    - Corrupted key_len: decoder reads past the record into the next
      one's header, treating remainder as next record's data. Insert a
      garbage MVCC entry into the memtable on recovery replay.
    - Corrupted val_len: returns wrong value bytes to subsequent
      VP-resolution reads.
  The block-level CRC32C in sstable/builder.rs:217 covers SSTable
  bytes but NOT the WAL — log_stream had no integrity protection at the
  record granularity. Modern SSDs/NVMe have low (not zero) error rates;
  ZFS/btrfs catch this at the filesystem layer; ext4 does not.

VP-offset CLEARED:
  Audit 1 #4 raised concern about VP offset corruption returning silent
  wrong bytes. Verified crates/partition-server/src/sstable/builder.rs:217
  — block CRC32C covers `[entries + offsets + num_entries]`, and VP
  entries (OP_VALUE_POINTER) live inside the block's entries section. So
  a bit flip in a stored VP offset is caught at block read time. No fix
  needed; documented as cleared in F158's feature_list entry.

How:
  New module `crates/partition-server/src/wal_record.rs` (~270 LOC)
  defines a versioned record codec:

  - V0 (legacy): unchanged on-disk format. Existing log_stream records
    keep working post-F158.
  - V1 (post-F158): [0xff sentinel][length:4 LE][V0 payload][crc32c:4 LE]
    The 0xff sentinel is unambiguous because no valid V0 op byte can
    be 0xff (ops are 1, 2, optionally OR'd with 0x80=OP_VALUE_POINTER,
    never 0xff). crc32c covers `length_bytes || payload_bytes` so a
    corrupted length is caught before its value is trusted.

  Decoder dispatches per-record on the first byte:
    - 0xff → V1 path with CRC verify; mismatch → DecodeOne::Corrupt
      with skip_bytes (= envelope total) so caller can advance past.
    - else → V0 legacy path.

  Five call sites updated to use the shared codec:
    1. start_write_batch (background.rs:447) — emits V1 envelope segments
    2. GC re-write encoder (background.rs:1509) — emits V1
    3. decode_records_full (lib.rs:2951) — dispatches via codec
    4. decode_records_with_offsets (lib.rs:2975) — dispatches via codec
    5. process_gc_chunk inline decoder (background.rs:1419) — dispatches
       via codec
    Plus: encode_record (lib.rs:2940, used by tests) now emits V1.

Migration:
  Forward-compatible. V1 binaries write V1; V1 decoders accept both
  V0 (legacy on-disk pre-F158) and V1 (new writes). V0 binaries on V1
  data would interpret 0xff as op byte → bounds check probably fails →
  some records skipped silently. Acceptable for restart-all-together
  model.
