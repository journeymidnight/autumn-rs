【根因】
  抢先 roll 在一次成功 append 的 end 达到 16 GiB 时触发,直接封存并换 tail,不排空。
  而 PS 在一条 stream 上并发跑 8 个 phase2,滚动方只是其中之一。同一时间窗两侧:
  - 在 ResetTail **之前**完成的兄弟:被连续前缀规则 ack 成功,offset 却在封存点之上。
    WAL 重放按 sealed_length 截断 → 已 ack 的字节在恢复时不存在。**静默丢数据**。
  - 在 ResetTail **时仍在飞**的兄弟:完成后被套用到新 extent 的状态(commit=0),
    落进 pending_acks 里一个永远够不到的 key,调用方的 oneshot 被永久扣住。
    PS 的 phase2 是无界 ack_rx.await → 分区停止应答 → 连接不再读 socket。

【为什么之前三次都找错】
  没有日志(这条路径只打 debug)、读正常(读不走 worker)、EN 空闲(早就 ack 完了)、
  撤掉负载也不恢复(sender 躺在活着的 map 里)、1600 秒超过所有下游超时(等的是
  BTreeMap 里的一个 oneshot,不是任何 I/O)。每一条都把我推向错误的层。
  真正收窄范围的是那条"分区收下请求后不回复"的诊断。

【修法】
  抢先 roll 走 SealCommit 排空(和其余六个发送点一致)。apply_completion 拒收
  extent_id 不是当前 tail 的完成——这是**可达的**兜底(软错误 tail 重载无法 quiesce,
  而且本次改动放大了它的窗口),不是不变式,注释里写明了。

Task scope: 找到并修复分区永久卡死的真正根因——per-stream worker 的生命周期与它的
  "tail 已初始化"标记不是同一条命,而且退出的 worker 会注销掉自己的继任者。
  后果是三副本各截掉 1.7 GiB。已修、fable 独立评审、评审项全修、两处消融各自验证。

【线上现象】
  - 三个副本在同一时刻各丢 1.7 GiB,append 带 commit=0;随后 manager 把该 extent
    封在 8 MiB,而节点上有 3.3 GiB(UNDER-SEAL)。
  - 分区停止应答写入,客户端每分区堆 100-220 MiB 未读请求;无任何 WARN/ERROR。

【机制(评审纠正了我第一版的说法)】
  没有任何东西"把 commit 归零"——零从来没被覆盖过。新 worker 出生即 cursor=0,
  而唯一会把 cursor 抬到已提交长度的 SeedCursor 就在被跳过的那次初始化里。
    split → invalidate_stream(清 worker + 标记) → append spawn worker#2,初始化完成
    → worker#1 这才排空退出,按 key 删掉了 #2 的条目
    → 下次 append spawn #3,看到标记仍为 true 就跳过初始化
    → 第一个 append 报 "no tail set" → 被当软错误重载 tail → 重试在 cursor 0 处 lease
    → header.commit=0 → 每个副本照做,截断。

【修法】
  - 每个 worker 带 generation,两处删除都以它为门。
  - 顺序是承重的:把"清标记"挪到 generation 检查之前,所有显而易见的测试仍然全绿,
    但会让一个活着的 worker 在自己脚下重新初始化——两个 worker 用各自的 cursor
    写同一个 extent,比原 bug 更糟。已用测试钉死这个顺序。
  - "no tail set" 改为 fail-fast,不再软重试:下次再出生命周期 bug 会报错而不是截断。

Main gaps: 已卡死的 3 个分区需重启清除;FTW 上传停在 dsv4 8/52、minimax 29/34。

  `2>/dev/null` 之于 dd,等同于 `e.to_string()` 之于 PS 的错误链:**都丢掉了区分失败与缺席的通道**。

【2026-09-02 更正:FreeToken 从未挂起 —— 我的第三次同型仪器错误】
  事实: MiniMax 的加载**成功完成了**。串行专家构建 09:28:39 开始、09:49:38 打出
  "Free memory after initialization: 1.84 GiB" —— 21 分钟,慢但正常。
  我的错误: 用 `rchar` + 5 秒 CPU 采样判定"完全静止、0 I/O",据此宣布挂起。
  但串行路径走的是**文件 mmap**(expert_banks.py 注释明写 "reclaimable file mmap"),
  而 **mmap 的缺页不计入 rchar**。仪器看不见那种活动。

  三次同型错误,记在一起因为它们不是三个偶然:
    1. `ops history` 看不见 auto-policy 的 EC 转换(绕过 op ledger)-> 误证伪了正确假设

       还让 subagent 花两轮论证一个伪事实
