Audit context (this iteration):
  Two parallel Explore agents — read-path corruption + atomic file/cross-file
  ordering. Read-path audit verdict: codebase mostly clean post-F155-F158.
  Only 1 HIGH hypothesis (cross-replica byte divergence in

  + 1 missing fsync in save_meta. F159 ships fixes for both.

Why:
  Bug 1 — save_meta not fsync'd (extent_node.rs:1332).
    Pre-F159 used `compio::fs::write(path, buf)` which writes via the page
    cache without fsync. The 44-byte V1 .meta could remain page-cached for
    unbounded time; a host crash before OS background flush would lose the
    write. On restart, parse_meta returns whatever state .meta had at the
    previous successful flush — silently rolling back metadata even though
    F157's CRC trailer is intact (CRC validates against OLD durable bytes,
    can't detect "stale but valid").

  Bug 2 — apply_extent_meta_durable writes .meta BEFORE fsync'ing .dat
    (extent_node.rs:1820-1830).
    Pre-F159 order: (a) update in-memory atomics, (b) save_meta writes .meta,
    (c) sync_data on .dat. Crash in b→c window: OS may have flushed .meta
    (44 bytes, well under one sector) while .dat's must_sync=false bytes
    were still in page cache and lost. On restart parse_meta returned NEW
    sealed_length while .dat file size was SHORTER — reads past durable
    extent.len returned EOF or zero-padded bytes, masquerading as
    successful seal. F143's sync_data was load-bearing but the wrong order
    made it ineffective.

How:
  Fix 1 (save_meta): replace `compio::fs::write` with
    OpenOptions::new().create.truncate.write.open + write_all_at + sync_data.
    The .meta is always durable on return.

  Fix 2 (apply_extent_meta_durable): reorder — fsync .dat FIRST (data
    durable up to new sealed_length), THEN save_meta (which now also
    fsyncs .meta). Even if a crash strikes between, the worst observable
    state is "old .meta + new .dat" which restart treats as still-unsealed;
    manager re-applies seal on next contact. No silent corruption.

Cost:
  Each save_meta call now does one extra fsync (the .meta). save_meta runs
  on owner-revision changes, eversion bumps, seal applies, recovery — all
  rare events. Negligible perf cost.
