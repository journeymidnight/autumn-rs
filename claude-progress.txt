MULTI-PS STATUS (answer to the user's question)
=========================================================================
1. MULTI-PS REGISTRATION/DISCOVERY — SUPPORTED.
   - Manager keeps a PS registry: MetadataState.ps_nodes: HashMap<ps_id, addr>
     (crates/manager/src/rpc_handlers.rs), heartbeat liveness in
     ps_last_heartbeat. RPCs: register-PS, heartbeat-PS (unknown ps_id →
     CODE_NOT_FOUND → PS self-evicts). PS liveness loop evicts a PS that
     misses its heartbeat window, then rebalances.

2. PARTITION FAILOVER (PS dies → another PS opens the partition) — SUPPORTED.
   - Each partition has exactly ONE owner PS: MgrRegionInfo.ps_id.
   - On PS eviction, rebalance_regions() reassigns its partitions to the
     remaining least-loaded PS and persists to etcd.
   - PS polls the manager (sync_regions_once, ~2s); when a region's ps_id ==
     self it open_partition()s (replays log_stream from the VP checkpoint),
     and drops partitions no longer assigned to it.
   - Split-brain prevented by owner-lock revision fencing: the new owner
     acquires a higher revision; the old owner's appends/commits are refused
     (durable owner_revision fence, Item 1 / db5d708).
   - Covered by crates/manager/tests/system_ps_failover.rs (PS1 dies → keys
     reassigned + recovered on PS2).

3. CROSS-PS PARTITION MIGRATION (proactive move for load balance) —
   NOT SUPPORTED (by design). No migrate/move/transfer RPC exists.
   rebalance_regions() is REACTIVE only (fires on register / upsert / split /
   PS eviction) and PRESERVES existing assignments while the owner is healthy.
   Load rebalancing today is indirect: operator-driven split (relief valve) /
   merge shifts partition boundaries; the manager is mechanism, policy is
   external (F183/F185, see project_auto_split_before_merge memory).
   → A graceful "drain partition A from PS X to PS Y without killing X" path
     does not exist. If wanted, it is a NEW feature (proactive-migrate RPC:
     freeze-source → seal/handoff owner-lock → open-on-target → reroute
     clients). Relevant caution: the drain-before-reopen attempt in the
     reopen-overlap work DEADLOCKED on client port migration (see history),
     so a migration design must solve old↔new handoff carefully.
