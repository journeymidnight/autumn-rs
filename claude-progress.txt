F209 sub-features:
  F209-A `handle_get_partition_detail` leader gate
    - crates/manager/src/rpc_handlers.rs:2590-2620
    - Without it, follower returned CODE_OK + zeroed PartitionLoad —
      client info --detail couldn't tell "no metrics yet" apart from
      "queried follower".
    - Same CODE_NOT_LEADER early-return pattern as handle_force_ec_convert.

  F209-B `apply_recovery_done` slot-mismatch marker release
    - crates/manager/src/recovery.rs:194-217
    - Before: when extent_slot returns None inside the borrow_mut, the
      handler did `return Err(Precondition)` WITHOUT releasing the
      Recovery marker — invariant I3 violation. F208 sweep was the
      only cleanup, blocking the extent for up to 10 min.
    - Fix: hoisted the slot-None check to a new branch before the
      borrow_mut. Same release pattern as the existing layout_changed
      Some(true) arm. The inner slot None branch becomes unreachable
      (kept defensively).

  F209-C F208 sweep excludes ConvertToEc from auto-release
    - crates/manager/src/extent_inflight.rs::sweep_stale_inflight_once
    - Risk: F208 auto-released ALL stale kinds. For ConvertToEc, that
      opens a race with the original EN-side dispatch: a fresh
      force-ec-convert in the release gap can shuffle a DIFFERENT
      parity-node assignment; manager state then records the second
      dispatch's target_nodes while the first dispatch's bytes are
      what physically landed. Exactly the failure mode F198's rich
      marker was added to prevent.
    - Fix: ConvertToEc is WARN-only. Recovery + Delete still
      auto-release. Operator manually remediates ConvertToEc (Python
      ops: confirm EN finished, then etcdctl del).
    - Tests: existing f208_sweep_auto_releases_stale_markers updated
      (expect 2/3 released, ConvertToEc survives). New
      f209_c_sweep_excludes_convert_to_ec_from_auto_release.

  F209-D `handle_force_ec_convert` verify-BEFORE-acquire
    - crates/manager/src/rpc_handlers.rs:2545-2640
    - Bug: new_eversion captured from a clone taken BEFORE the
      alloc_extent_on_node awaits + the acquire_extent_inflight await.
      During those awaits, a concurrent apply_recovery_done for the
      same extent could complete (no ConvertToEc marker yet to block
      it), bumping ex.eversion. The dispatch loop's
      apply_ec_conversion_done would then write the stale new_eversion
      to etcd, silently undoing the recovery.
    - Initial form (committed in 444ede0): verify-AFTER-acquire with
      drain-on-mismatch. Codex review flagged: if
      drain_extent_inflight_marker fails (NotLeader or transient etcd
      error), the stale marker persists in etcd and the dispatch
      loop applies the stale state — the bug F209-D was meant to
      prevent.
    - Revised form: verify-BEFORE-acquire. Re-read ex.eversion under
      a fresh borrow before acquire_extent_inflight. If different,
      return Precondition WITHOUT writing a marker. No drain needed.
      After our acquire succeeds, F207's exclusive CAS + other
      mutators' refuse-at-start guarantees ex.eversion is frozen
      until our apply runs.

  F209-E F207 apply-done atomicity integration test
    - crates/manager/tests/f209_apply_done_atomicity.rs (#[ignore])
    - Two tests:
      * f209_e_apply_ec_conversion_done_atomic_success: acquire +
        apply → both effects landed.
      * f209_e_apply_ec_conversion_done_atomic_failure_under_deposed_leader:
        acquire + externally overwrite leader key + apply →
        Err + NEITHER effect lands.
    - Visibility plumbing: apply_ec_conversion_done /
      acquire_extent_inflight / extent_inflight_key /
      EXTENT_INFLIGHT_PREFIX / ExtentOpPayload / ExtentOpKind bumped
      pub(crate) → pub. mod extent_inflight → pub mod.
