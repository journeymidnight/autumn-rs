Why this exists: the adapter had two code paths, and only one was native. Rust hands LanceDB a store OBJECT through ObjectStoreParams.object_store — a field only a caller compiled against lance can reach. A prebuilt wheel never sees it; Python resolves a store from the URL SCHEME inside its own bundled Rust core. So Python's only route was a FUSE mount, which docs/lancedb_validation.md itself marks as the weaker path (nontransactional multi-key metadata, per-mount serialization, single-mount only).
WHAT WAS VERIFIED BY READING lance v13.0.0-beta.6 AND lancedb df5709ef, not inferred: ObjectStoreProvider (lance-io object_store/providers.rs:42) and ObjectStoreRegistry::insert (:418, takes &self) are public; Session::store_registry() (lance/src/session.rs:301) reaches a live session's registry; ObjectStore::new(Arc<DynObjectStore>, Url, ...) (object_store.rs:1800) is a public constructor. Therefore NO lance fork is needed — the patch is confined to lancedb-python. The ObjectStore struct's own fields are mostly private, so the struct-literal form the in-tree providers use is not available out of crate; the public constructor is the only door.
THE SECOND REGISTRATION SITE, which is the easy thing to get wrong: lancedb.connect(session=None) does NOT go through the Session class. python/src/connection.rs:926 only set a session when one was passed, and the builder's own fallback is Arc::new(Session::default()) (verified at database/listing.rs:464,569,644) carrying the stock registry. Patching Session alone would leave the default connect() unable to resolve the scheme. Both connect entry points now install the provider, and the demo takes --with-session precisely so both paths get exercised.
URL shape, and why the scope is NOT in it: the manager rides in the authority (autumn://host:port/path) so a dataset URI is self-contained. A missing scope is an error, not a default. The scope is also folded into calculate_object_store_prefix, which is the registry cache key (providers.rs:290) and build_store's metrics base.
