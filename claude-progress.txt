Why:
  Both `current_commit` (`client.rs:1332`) and `commit_length_for_extent`
  (`client.rs:1689`) iterated over all replica addresses, `continue`d on
  any error (RPC failure, decode error, non-OK code), and computed the
  minimum over WHATEVER subset responded — accepting even a 1-of-N
  response. The min-replica commit protocol's correctness invariant is
  that the consensus position is bounded by EVERY replica's local length;
  taking the min of a strict subset can return a position HIGHER than
  what the unreachable replicas actually hold. After an append at that
  speculative position, the data exists on only the lone responder. If
  that responder dies before the unreachable peers re-replicate the
  speculative bytes, the data is permanently lost — and the manager's
  metadata still references those bytes, so partition open at restart
  fails to load any SST whose ValuePointers reference the lost range.

Concrete failure mode (R=3):
  - A/B/C all at offset 100.
  - Network partition: B+C isolated from manager + client.
  - Client probes commit_length: A responds 100, B/C unreachable.
  - Pre-F156 returns 100 → client appends bytes 100..200 → A acks →
    manager records sealed_length using this offset on next seal.
  - A crashes. B+C return with bytes 0..100 only.
  - Recovery tries to re-replicate 100..200 from a healthy source;
    none exist (A is dead).
  - Bytes 100..200 lost. Restart: SSTs whose VPs reference the lost
    range fail to load on partition open.

How:
  Track `success: usize` alongside `min_len`. After the loop, require
  `success >= total / 2 + 1` (majority quorum). If below, return
  `Err(insufficient quorum...)`. The worker's existing soft-error retry
  path waits + reloads tail + retries, which converges once the
  partition heals or the manager evicts the stale node and
  re-replicates.

  Quorum threshold = ⌊N/2⌋+1 (Raft / Paxos majority):
    R=1 → 1 (no fault tolerance, but no quorum to violate)
    R=2 → 2 (no fault tolerance — single-replica response not safe)
    R=3 → 2 (tolerates 1 dead)
    R=4 → 3 (tolerates 1 dead)
    R=5 → 3 (tolerates 2 dead)

Trade-off:
  Pre-F156 the system would continue writing on a single-survivor
  majority-failure scenario (silently unsafe). Post-F156 writes halt
  until ⌊N/2⌋+1 replicas can be reached. This is the correct durability
  trade-off for a strongly-consistent system: refuse to make progress
  on insufficient information rather than silently risk data loss.
  Production clusters running in degraded mode (≥1 replica dead) still
  make progress as long as quorum is reachable.

F154 candidate retracted:
  The previous round's audit agent reported `flush_one_imm_local`
  (lib.rs:3257-3300) as a VERIFIED-VIOLATION of F148-A invariant P3.
  Re-inspection shows this was a misreading. F148-A's P3 requires no
  `.await` between (a) the snapshot-capturing borrow_mut DROP and (b)
  the mpsc-send inside save_table_locs_raw. In flush_one_imm_local:
    - Lines 3277-3292: borrow_mut block (no awaits inside), captures
      tables_snapshot at line 3291.
    - Line 3292: borrow_mut drops (end of block).
    - Line 3297: save_table_locs_raw call (synchronous up to mpsc-send
      inside the function; first await is on ack_rx after the message
      lands in the per-stream worker FIFO).
  Path 3292 → 3297 contains only `};` and the function call — no awaits.
  The awaits at lines 3267-3272 (spawn_blocking + part_sc.append) happen
  BEFORE the snapshot-capturing borrow_mut, which is fine — any
  concurrent `do_compact` mutations to `p.tables` during those awaits
  are reflected in the snapshot taken AFTER those awaits. The F148-A
  invariant holds in both flush_one_imm and flush_one_imm_local.
  Lesson: an audit agent saying "VERIFIED-VIOLATION" with file:line
  references still warrants independent re-inspection before a fix —
  agents can confidently misread invariants whose subtleties live in
  inline comments.
