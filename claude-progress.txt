Round 2 findings:

  HIGH (re-opens MED-4): compact paths stamped last_compact_at AFTER
        clearing compact_inflight. Between them sat a logging match,
        truncate(...) network await (seconds), and pending bytes
        compute. Scheduler tick reading the (inflight, last_at,
        pending) tuple could see (0, stale-0, stale-high) for a
        partition that had JUST finished compacting → redundant
        dispatch. Fix: stamp + refresh BEFORE clear in the do_compact
        Recv path AND the expiry-major Timeout path. GC loop already
        had correct order; only compact paths inverted it.

  MEDIUM (re-opens HIGH-2): two GC early-continue paths skipped the
        last_gc_at stamp:
          - get_stream_info failure (transient manager/extent-node hiccup)
          - extent_ids.len() < 2 (single-extent partition)
        Cooldown gate read 0-as-never on these continue paths, letting
        the scheduler re-dispatch every 5 s. Fix: extract
        `stamp_last_gc` closure helper, call on every continue path
        (and refactor the already-correct empty-holes + main-tail
        paths to use the same helper for consistency).

  LOW: GC drain `(Auto, Force)` collapse silently drops the Auto.
        Force is operator-named extents; Auto is threshold-based scan
        of top-3 high-debt extents. Generally different extent sets.
        Fix: documented as accepted one-tick (5 s) deferral — the
        Auto's high-debt extent gets re-dispatched on the next
        scheduler tick once this run's stamp engages cooldown then
        re-evaluates urgency.
