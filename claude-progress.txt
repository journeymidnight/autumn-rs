Task scope: F166 — Eliminate `&mut` aliasing UB on `UnsafeCell<CompioFile>`
            in extent_node.rs (memory-safety audit finding). Two sites
            converted to use compio's safe `&File` AsyncWriteAt impl
            (uses SharedFd internally). One file-replacement site
            (line 2314) deferred to a future Rc<File> refactor.

Why:
  A focused memory-safety audit (this iteration, distinct from the
  prior 8 wire/disk/race audits) flagged two sites in extent_node.rs:
    - file_pwrite (line 435): `let f = unsafe { &mut *file.get() };`
    - build_append_future (line 937): same pattern

  Both held `&mut CompioFile` across `.await`. The historical SAFETY
  comment claimed "compio is single-threaded so &mut aliasing is
  serialised per-future" — but Rust's `&mut` exclusivity rule is at
  the LIFETIME level, not the temporal level. Two compio futures on
  the same runtime each holding a `&mut` across awaits have
  overlapping lifetimes the compiler is allowed to reason against,
  even when only one polls at a time. UB the compiler may exploit.

How:
  compio provides `impl AsyncWriteAt for &File` (compio_fs/file.rs:250)
  which uses `SharedFd` interior mutability internally — write_at on
  `&File` is just as efficient as on `&mut File` (in fact the
  `&mut File` impl just calls the `&File` impl). Switching to a
  SHARED reference via `&*file.get()` makes the pattern legal:

    Pre-F166: let f = unsafe { &mut *file.get() }; f.write_*at(...)
    Post-F166: let mut f: &CompioFile = unsafe { &*file.get() };
               f.write_*at(...)

  The `let mut f` makes the BINDING mutable. Autoref builds
  `&mut &CompioFile` which is the receiver type for
  `AsyncWriteAtExt::write_all_at` on the `&File` impl. Shared refs
  to UnsafeCell content can alias freely (that's exactly what
  UnsafeCell is for); concurrent writes are serialised by the
  kernel/io_uring at the syscall level (not by Rust's borrow
  checker, which doesn't need to know).
