【2026-09-02 direct-read 对 EC 不友好：已修（8abef44）】
  `extent_read_descriptor` 把"EC 转换过"/"payload 不在 .dat"/"真故障"三件事一律当 `Err`，
  于是 PS 对前两者也打 WARN —— ≥4 EN 就默认装 EC，等于每次大值读一条告警，真故障淹死在
  里面。改成 `ReadDescriptor::Direct | NotDirect(EcConverted|PayloadOutsideDat)`，真故障仍
  是 `Err`；`EcConverted` 降 debug、`PayloadOutsideDat` 反而升 WARN（它要求 payload_location
  与 ec_converted 不一致，而这两个字段是同一个 etcd 事务发布的，属于不该发生）。
  **顺带修掉一个真的用户可见延迟 bug**：批量重定向对拒绝回 `Unavailable` ⇒ SDK 当瞬时错误，
  烧满 10 次刷新退避（≈9~13 秒）才轮到逐项代理回退 —— EC 集群上每次批量直读都卡这么久，
  而 `--direct-read` 默认开着。改回 `FailedPrecondition`（在确定性短路集合里）立即降级。
  EC 直读本体按用户顺序**只立账不实现**（F-EC-DIRECT-READ）。账里更正了一条初版写错的
  论断：**别指望 k 路扇出提速** —— shard_size 是按 extent 算的（seal 阈值 16 GiB、下限
  1 GiB），k=4 时每片数 GiB，一个 8 MiB 的 value 只落 1~2 片，永远不是 k 片。

  **为什么划不来（评审挖出来的代价，重做前先读这三条）**：
    · **`panic = "abort"`**（release profile）⇒ 网关线程一 panic **带走整个 PS**。
      "worker 死了不拖垮 PS"只对"返回 Err"成立。sidecar 时代 panic 只死 sidecar ——
      这是搬进程内换来的真实代价，**进程内无法消除**。
    · **传输是进程级 `OnceLock`**：`--transport ucx` 的 PS 会让网关也走 UCX（未验证，
      且 fuse core 有 UCX 栈 abort 前科，叠加 panic=abort 就是 PS 宕机）。
    · **`--cpuset` 管不住网关线程**（它只喂给分区/shard runtime 给自己钉核，不设进程
      亲和掩码）⇒ 网关会跑到分区线程的核上，也躲不开租户核。
  **收益比原以为的小**：唯一站得住的好处是 GPU 节点少收一次（sidecar 时代它先网络收、
  再 loopback 收）。"网关不出存储节点"是错的 —— 副本选择是哈希轮转、无本地性偏好，
  多节点集群上多数读仍来自远端 EN。
  【顺带记两条通用坑，与本次去留无关】SO_REUSEPORT 下端口被别的进程占着**照样 bind
  成功**（两个网关同端口会各分走一半连接，不会有一个拒绝启动）；监督线程按 handle 顺序
  `join` 会让高序号 worker 的死讯被低序号挡住，要让 worker 自报（Drop guard 才能覆盖 panic）。

【2026-09-02 批量 RPC 零拷贝（wire v31 + v32），并纠正一次错误结论】
  用户指出 bulk 判据加错了量：加在**单条 value** 上，所以 256×4 KiB 的批量哪怕在线上是
  1 MiB 的一帧也走拷贝路径。已实现 `MSG_BATCH_PUT_BULK`(0x5A,v31) 与
  `MSG_BATCH_GET_BULK`(0x5B,v32)，判据改按**分组总字节**；帧格式没动（`value_len` 本就是
  尾巴总长，切点写进 ctrl）。PS 侧从尾巴切 `Bytes` 直喂 `WriteOp::Put`（下游本就收 Bytes）。
  实测（同集群、只差一行的两个二进制交替取样）：
    写 TCP loopback 4 KiB   103.8 → 103.7   0%（**op 绑定区间**，见下）
    写 TCP loopback 32 KiB  450.6 → 523.1   +16%
    写 RoCE(rc_mlx5) 4 KiB   57.9 →  93.3   约 +61%（inline 还在 47~68 抖，bulk 稳 93.3）
    读 真实查询负载(41 query/5164 chunk)  13054 → 12070 ms  -7.5%
  **我先判定"不值得做"是错的，两处错因都记下来**：①测量点选在单分区 ~30K ops/s 的 op
  天花板上（26.5K ops/s），省 CPU 根本显示不出来；②只测了 loopback TCP，而零拷贝最占
  便宜的恰恰是生产用的 RDMA。另一个被 fable 审计从代码上驳回的推理：我以为"批量已摊薄
  bulk 收益"，实际 inline 批量对逐字节拷贝一点没摊薄，且 `extract_part_id` 为读一个
  part_id 就把整帧完整反序列化、`check_layer_a` 再来一遍，一个 256-op 帧多约 1500 次分配。
  【顺带修的真问题】连接回复路径的 `write_vectored_all` **没有 IOV_MAX 分段**（一条回复
  以前最多 2 个 buffer 所以够不着上限，N 值回复能够着；内核按**条数**拒绝且会打死写线程）；
  `get_many`/PS 指南里"batched read 不走 partition_loop"的说法是**错的**（它确实绕
  partition_loop、会阻塞 group-commit），新形式改成在连接线程上服务后才成立。
  【踩坑记录，已写进 docs/ops.md「A/B-ing a wire-path change」】①`cluster.sh reset` 后

【2026-09-02 下半场:FUSE 根因、集群重建、上传实测】
  ■ FUSE 把节点搞死的根因(已修,344a37f)
    挂载 FUSE 后内核成为进程的客户端:mountpoint 下的 stat() 会把调用者置于 D 状态
    等守护进程应答,而 D 状态杀不掉。容器运行时建/拆 sandbox、exec 都要 stat 挂载点,
    所以只要一个线程踩进去就永远回不来、还攥着锁 ⇒ 节点起不了任何新容器,
    但已在跑的进程完全正常(它们不经过 containerd),节点还一直 Ready(心跳不碰挂载点)。
    四处修复:
      1. MountOption::AutoUnmount —— 主修复。以前唯一的卸载路径是优雅退出时的
         Mount::drop,SIGKILL/OOM/未处理的 SIGTERM 全都会留下活挂载。
         它还把残余的"永久阻塞"变成"调用方拿到错误"。
      2. 异步 Read 加超时(REPLY_TIMEOUT)。**这条可能才是真凶**:守护进程"死了"内核会
         中止连接给 ENOTCONN;真正永久阻塞的是"活着但不应答",而昨晚 manager 卡死 3 小时
         期间 autumn-fuse 正是这个状态。其他 op 走 call_sync 有超时兜底,只有 Read 没有。
      3. Read 的 unbounded_send 失败时把 reply 取回来回 EIO(原来直接丢弃,注释还错写成
         "fuser 会超时"—— FUSE 没有超时)。
      4. entrypoint 的挂载前清理不再用 `mountpoint -q`(那是一次 stat,必然卡在残留挂载上,
         于是"清理崩溃前任"的检查把接任者卡死),改读 /proc/mounts + 惰性卸载。
