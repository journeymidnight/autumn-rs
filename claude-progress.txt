Task scope: F200 — proper fix for the EC sub-range fall-back path.
            Replaces "decode whole extent on any shard-read failure"
            with sub-range RS reconstruction.

User-corrected analysis (2026-05-14):
  - F199 was a workaround (suppress retries). The real bug is in
    `ec_subrange_read`'s fall-back path: on ANY single per-shard read
    failure it calls `ec_read_full_and_slice`, which reads ALL K+M
    shards at full size (length=0) and decodes the whole extent to
    slice the requested sub-range.
  - For a 64 MiB GC chunk read on a 2.8 GB EC(3+1) extent, this means
    4 × 933 MiB ≈ 3.7 GiB cross-network for what should be a
    K × 64 MiB ≈ 192 MiB reconstruction.
  - The 3.7 GiB amplification saturates macOS, causes manager's df
    probe to time out, marks healthy disks offline. F199's cooldown
    suppressed retries but didn't fix the amplification on the first
    attempt.

Why sub-range reconstruction works:
  - Galois-8 RS encodes byte-by-byte across K+M shards.
  - At each row position i, the K+M shard bytes form an independent
    RS codeword.
  - So sub-range [a, b) on a missing data shard can be reconstructed
    from [a, b) on K healthy shards. No full-extent decode.

Fix:
  - `crates/stream/src/client.rs`:
    - `ec_subrange_read`: removed `fall_back = true → ec_read_full_and_slice`.
      Failed plan entries now collected in `needs_reconstruct: Vec<usize>`.
    - New helper `ec_reconstruct_shard_subrange(failing_shard_idx,
      sh_off, sh_len)`:
      - Reads [sh_off, sh_off+sh_len] from K+M-1 non-missing peers
        in parallel (5 s timeout each).
      - Stops when K succeed.
      - Calls existing `ec_reconstruct_shard` on K-aligned
        sub-shards (offloaded via spawn_blocking — RS math is
        CPU-bound).
      - Eversion-stale short-circuits to the top-level retry loop.
  - `crates/stream/src/erasure.rs`:
    - 2 new unit tests pinning the load-bearing invariant
      "ec_reconstruct_shard works on sub-range slices":
      - f200_reconstruct_shard_subrange_data_shard
      - f200_reconstruct_shard_subrange_with_one_parity_present

Bytes-on-the-wire (user's GC scenario, 64 MiB chunk on 2.8 GB
EC(3+1) extent, shard 0 fails):

  - Post-F200: 3 × 64 MiB = 192 MiB. → 20× reduction.
