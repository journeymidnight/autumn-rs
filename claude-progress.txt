TaskStatus: completed
Task scope: F172 — Manager dispatch-loop CPU audit. Two concrete
            inefficiencies fixed; the rest of the dispatch loops
            cleared as already-clean.

Why:
  The manager runs ~7 background dispatch loops on a single compio
  runtime alongside its 18 RPC handlers (heartbeat_ps, register_ps,
  get_regions, mutating handlers). Any inline CPU work between
  awaits in a dispatch loop blocks all RPC handlers + sibling loops
  on the same runtime — same thread-per-core principle the
  partition-server side enforces post-F168/F169/F170.

Audit findings (cleared, no fix needed):
  - ec_conversion_dispatch_loop (recovery.rs:586-610): already
    filters under borrow before cloning candidates. Good pattern.
  - extent_delete_loop (extent_delete.rs:50): drains queue then
    sequential per-replica RPC. Each RPC awaited.
  - ps_liveness_check_loop (lib.rs:791): filter under borrow,
    only `dead_ps: Vec<u64>` clones cross the await.
  - recovery_collect_loop (recovery.rs:378): only clones small
    `s.nodes` map; per-node RPC dispatch with awaits.
  - disk_status_update_loop, leader_keepalive_loop,
    leader_election_loop: small constant work per tick.
  - rebalance_regions: O(parts × PS), bounded ~10 ms at 10K × 100,
    accepted.
  - replay_from_etcd: startup-only.

Fixes:
  F172-A — recovery_dispatch_loop snapshot pre-filter:
    Pre-F172: `s.extents.values().cloned().collect::<Vec<_>>()`
              clones EVERY extent, even the ones the loop body
              skips on its very first line.
    Post-F172: filter under borrow first
              (sealed_length > 0 AND not in ec_conversion_inflight)
              then clone only the matching set.
    Cost saved: at 10K extents (~200 B each with 4 Vec fields)
                = ~2 MB inline memcpy + ~40K heap allocs per 2 s
                tick → ~few KB / few µs after F172-A.
                At 100K extents = 20 MB / 400K allocs / 10-20 ms
                inline → mostly flat.
    Correctness: F138's apply-time re-check on
                 apply_recovery_done / mark_extent_available /
                 handle_multi_modify_split protects against the
                 stale-snapshot race window.

  F172-B — ec_conversion_dispatch_loop hoist node_addrs:
    Pre-F172: re-collected `s.nodes -> address` map ONCE PER
              CANDIDATE EXTENT inside `for (ex, stream) in
              candidates`. Same map identical across all iterations
              of a single tick.
    Post-F172: snapshot once alongside candidates under the same
               borrow.
    Cost saved: N candidates × M nodes of String clone per tick →
                M nodes total per tick. At 50 × 100 = 5000 →
                100 saved.
