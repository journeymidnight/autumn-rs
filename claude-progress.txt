Trigger (real-cluster incident 2026-05-15):
  User hit `force-ec-convert --extent 28` repeatedly failing with
  `extent 28 has in-flight Recovery; retry after it completes`.
  Root cause: at some point during F207-A/B/C testing,
  recovery_dispatch_loop legitimately acquired a Recovery marker
  for extent 28 (commit_length probe timed out transiently).
  Manager restarted before apply_recovery_done ran. The
  `extent_inflight/28` etcd key persisted across F207-D restart
  and got loaded into the new leader's in-memory ledger. The
  F207-D stale-sweep was 5-min tick / 24-h threshold / WARN-only
  — operator had no automatic recovery path.

F208 design:
  - Sweep interval 300s → 60s (env
    AUTUMN_MGR_INFLIGHT_SWEEP_INTERVAL_SECS, floor 1).
  - Stale threshold 24h → 600s = 10 min (env
    AUTUMN_MGR_INFLIGHT_STALE_THRESHOLD_SECS, floor 60s).
  - Behavior on match: auto-release (not just WARN). One atomic
    `etcd put_and_delete_txn(delete=[extent_inflight/<id>])`
    under F149 leader fence, then `commit_extent_inflight_release`
    drops in-memory shadow. Delete markers also clear
    `delete_progress` entry.
  - Loop body extracted into `sweep_stale_inflight_once(now,
    threshold_secs)` async helper so unit tests can drive one
    tick with controlled time + threshold.

Safety argument (why auto-release is data-correctness-safe):
  Sweep ONLY touches the ledger marker. It does NOT mutate
  `extents/<id>` state and does NOT message any EN. If an
  EN-side task is genuinely still running when the marker is
  released, worst case is wasted retry work:
    - Recovery: EN completes, pushes recovery_done, next df
      probe drains it; apply_recovery_done runs with marker
      already cleared → no defer → apply proceeds normally.
    - ConvertToEc: EN F119-D + F153 idempotency make
      re-dispatch a no-op.
    - Delete: EN handle_delete_extent is idempotent.

Leader-failover-as-reconcile invariant:
  `started_at` is in the rkyv'd MgrExtentInflightRecord payload,
  persisted at acquire time. New leader's replay_from_etcd
  loads it unchanged, so the stale-detection clock continues
  across failovers. Markers that were already stale on the
  deposed leader get released by the new leader's sweep
  without needing any handoff. This is why F208 only does
  auto-release, not per-tick etcd reconcile:
    - The failover path naturally serves as a full reconcile.
    - Per-tick reconcile would only help "operator manually
      etcdctl del'd while same leader keeps running" — rare
      operator-error scenario whose supported remediation is
      "restart the manager".

What F208 does NOT change:
  - acquire_extent_inflight / release_extent_inflight_op / apply
    paths' release semantics — unchanged. The atomic
    put_and_delete_txn in apply paths is still the primary
    release mechanism (F207 invariant I3).
  - F208 sweep is the SAFETY NET for markers that escape that
    path.
  - F207-D/E "no backward compat with pre-F207 etcd state"
    policy — unchanged.
