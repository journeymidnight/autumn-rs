F-FS-UNIFY 设计文档(docs/fs_unify_design.md,已审批;原始提案记录):
  · 目标:fuse(POSIX mount)与 fsspec(Python)是同一文件系统的两个前端 ——
    同一 inode 布局、同一 per-inode lease 围栏,而非当前 F-FSSPEC-1 的独立
    `fs/` 命名空间(不同文件、互不围栏)。
  · 架构:一个共享 Rust FS core —— 把 crates/fuse 的 meta/dir/extent/read/write
    从 `fuser` feature 解耦(返回裸 InodeMeta,→FileAttr 转换上移进 dispatch.rs),
    fuse 二进制与新 PyO3 `autumn.Fs` 绑定共用;autumn_fsspec 重写成 shared inode
    布局之上的薄 facade(path↔inode、真 dirent、extent 读写)+ open/close 时
    autumn_client::lease acquire/heartbeat/release。
  · 关键既有支撑:lease 已是可复用库(autumn_client::lease);namespace core 已
    ~纯粹(ClusterClient + key/schema,仅 return 边界薄薄耦合 fuser)。
  · **前置 bug**:inode 分配器(meta.rs:alloc_inode)对 next_inode 计数器是
    非-CAS RMW → 并发分配者(fuse+fsspec 或双 mount)会重号 → 损坏。须改成
    crash-safe 多写(manager AllocInodes RPC 或 SDK CAS)。此项独立可先发,
    也顺带修当前多-mount fuse 的潜在隐患。
  · 分期 M0(分配器)→M1(解耦 core)→M2(PyO3 Fs)→M3(fsspec facade,退役
    `fs/` 布局)→M4(lease+围栏+跨面测试)。
  · 待用户定的开放问题:Q1 只写租约 vs 恒租约;Q2 分配器 manager-RPC vs SDK-CAS;
    Q5 Python 面 POSIX 语义广度。

用户复审提问("和 fuse 能访问相同文件吗?")→ 发现并修 latent bug:
  · fsspec 与 fuse 是同一集群的两扇独立门,NOT 同一批文件 —— fuse 按 inode
    键控([0x03][ino][off]),fsspec 按 path 键控;互不可见(故意:纯客户端
    不复刻 fuse 的 inode 分配 + lease 协调)。
  · **但**初版 fsspec 用了 \x01/\x02 前缀,与 fuse 的 inode(0x01)/dirent(0x02)
    **撞命名空间** —— 共享集群时 fsspec 根 ls(range \x01)会扫进所有 fuse
    inode。改到保留 `fs/` 命名空间(fs/m/ manifest、fs/d/ chunk;比照 kvcache
    `kvc/`、memory `doc/`)。真集群验证:注入 fuse 式 0x01/0x02/0x03 键,fsspec
    ls('') 完全无视之,且 fuse 键原样存活 → 二者可安全共享一集群。
  · 全量仍 33 passed(含 layout 前缀断言 + fuse 非碰撞断言更新)。
