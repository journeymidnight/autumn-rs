Bugs closed by F152:

  Bug 1 — handle_create_stream etcd-first violation
    File: crates/manager/src/rpc_handlers.rs:385-398
    Root cause: pre-F152 `s.streams.insert + s.extents.insert` ran BEFORE
      `mirror_create_stream(...).await`. Manager crash in await window leaves
      new leader (post-replay_from_etcd) without the stream record while
      extent files exist on remote nodes as orphans (eventually cleaned by
      F109/F113 reconcile sweep, but the stream record is lost).
    Fix: swap order — etcd mirror first, in-memory insert second. Symmetric
      to F125's fix on `handle_stream_alloc_extent`.

  Bug 2 — handle_update_stream_ec etcd-first violation
    File: crates/manager/src/rpc_handlers.rs:431-462
    Root cause: same anti-pattern. Higher impact than #1 because EC params
      drive `ec_conversion_dispatch_loop` — a crash mid-mirror leaves the new
      leader dispatching the OLD EC shape while the deposed leader's memory
      had the new one. Could materialise as `logStream value short` or
      `ec_read_full_and_slice: offset N past decoded payload` on subsequent
      reads (the F119-D corruption class).
    Fix: clone-then-mutate-then-mirror under read borrow, then apply to
      memory in a fresh `borrow_mut`.

  Bug 3 — handle_register_node etcd-first violation (both branches)
    File: crates/manager/src/rpc_handlers.rs:186-254
    Re-reg branch: `existing_node.shard_ports = ...; nodes.insert(...)` ran
      before `mirror_register_node(&existing_node, &[]).await`.
    New-node branch: `s.disks.insert + s.nodes.insert` ran inside the same
      `borrow_mut` that allocated IDs, before `mirror_register_node(&node,
      &disk_infos).await`.
    Root cause: shard_ports drives F099-K per-partition routing — a crash
      mid-mirror routes RPCs to the OLD shard layout until the next
      heartbeat re-corrects.
    Fix: both branches reserve IDs upfront, mirror to etcd, then apply to
      memory in a fresh `borrow_mut`. Wasted IDs from a failed mirror are
      safe per CLAUDE.md note 5 (`alloc_ids` derives `next_id =
      max(all_entity_ids) + 1` on replay).

  Bug 4 — truncate_to_commit no fsync after set_len
    File: crates/stream/src/extent_node.rs:1761-1782
    Root cause: pre-F152 the function called `file.set_len(commit).await`
      then `extent.len.store(commit, SeqCst)` with no `sync_data()`. The
      min-replica commit protocol depends on per-replica `extent.len`
      matching what the file actually holds on disk — if the node crashes
      after `set_len` but before any subsequent must_sync append flushes
      the file's metadata, post-restart the file size could be observed
      at the pre-truncate length (kernel hasn't durably persisted the
      inode shrink). Then the next `commit_length` probe reports a wrong
      consensus, and an append truncates the OTHER replicas back to that
      wrong value, diverging them at the same offset.
    Fix: `f.sync_data().await` between `set_len` and the atomic store.
      fdatasync is sufficient — the file size IS the data we need durable;
      subsequent appends sync content separately. truncate fires only on
      commit-reconciliation (rare), so the extra fsync cost is negligible
      on the hot path.

Out of scope (deferred to future features):
  - F153 candidate: `ec_conversion_inflight` not etcd-persisted → post-failover double
    EC dispatch. F119-D guard fires post-hoc only; the deposed leader's mid-`spawn_blocking`
    `ec_encode` window is exposed to a duplicate dispatch from the new leader. Fix sketch:
    new `ecConversionInFlight/$extent_id` etcd key with create_revision==0 CAS, mirroring
    the F149 `recoveryTasks/$id` pattern.
  - F154 candidate: `flush_one_imm_local` fallback violates F148-A invariant P3 (verified):
    `await spawn_blocking + part_sc.append().await` between borrow drop and next
    `borrow_mut`. Rare path (P-bulk spawn fail). Refactor: capture snapshot tuple
    synchronously before the await; ~30 LOC.
  - F155 candidate: rkyv `from_bytes_unchecked` on every wire deserialize + no schema
    versioning. UB on malformed input. HIGH for rolling upgrades + cosmic-ray-flipped
    bytes that pass TCP CRC; LOW for restart-all-together with trusted network.
  - F156 candidate: min-replica `commit_length_for_extent` continues on RPC error →
    uses `min` of REACHABLE replicas. Could commit at speculative position with only
    1/N respondents. Needs quorum enforcement + adversarial test first.
  - F157 candidate: MED-2 `handle_get → resolve_value` vs GC `punch_holes` (deferred
    since F148): per-extent reader-pin protocol; structural change.
